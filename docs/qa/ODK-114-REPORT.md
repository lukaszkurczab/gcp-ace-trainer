The accepted evidence limitation is explicit: the error screenshot comes from a temporary development rejection, not an organic native Keychain failure. The partial-removal retry test runs at storage level and does not include an app restart between failure and retry. Holding/removing screenshots contain a Metro banner that does not obscure recovery controls. These limitations do not change the final QA verdict under the PO-approved scope; they must not be represented as provider or physical-device evidence. The shared dirty worktree and release-manifest cleanliness are assessed separately before candidate freeze.

## Implemented

- Exact `encrypted_storage_key_missing` is carried as a bounded, typed bootstrap failure code. Other blocking states and unavailable-active content retain their existing surfaces.
- One stable recovery screen uses the existing `HoldToConfirmButton` and canonical `removeUnavailableEncryptedStorage()` operation. Retry only reruns bootstrap. Removal is single-flight; success remains until Continue; failure offers a full hold-to-retry and Return without claiming deletion.
- EN/PL copy, light/dark tokens, accessibility labels/roles/states, and a 2× text multiplier are present. No route, modal, storage migration, or automatic deletion was introduced.
- Follow-up QA correction: the recovery-only locale now reads native iOS `AppleLanguages`/`AppleLocale` because the encrypted language preference is unavailable with the missing key. It does not change the normal preferences provider or global i18n. The error surface has an icon plus text/alert, uses a bounded diagnostic code, and conservatively says that removal may have been partial instead of claiming nothing changed.

The error screenshot proves only that a rejected removal promise reaches the correct UI state; it does not prove a naturally occurring native Keychain failure.

Two attempts to induce a real removal error externally did not yield a reliable error fixture: making the disposable simulator's MMKV directory read-only did not prevent native deletion, and holding an exclusive SQLite transaction on the simulator keychain did not prevent Secure Store deletion. Directory permissions were restored to `0755`; the SQLite transaction was rolled back and closed. The perturbed installation briefly reached a generic bootstrap failure after Continue and was replaced by a clean disposable installation. A clean repeat passed success → Continue → ready. Neither failed fault attempt is counted as `error` evidence.

A third disposable-only fault attempt replaced one MMKV slot file with a directory while the missing-key screen was already open. Native deletion still reported success, so this is also **not** error-state evidence. The original 16,384-byte slot file was restored from the temporary backup; no backup remains. The deterministic storage test now covers a Secure Store removal exception after MMKV deletion and successful repeated reset, but it does not exercise the rendered error state or prove recovery after an app restart between those steps.

A fourth disposable-only fault attempt held an exclusive transaction on the **actual** simulator keychain debug database during removal. This blocked the native Secure Store operation and kept the UI at Removing; it did not produce an error-state screenshot. The transaction was rolled back and closed, after which the same operation reached Success. This long-running native lock is a timeout-resilience concern, not proof of a recoverable deletion error. No lock remains open.
