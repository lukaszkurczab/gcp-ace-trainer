# Patternly — roboczy rejestr obserwacji z przejść E2E

Plik służy wyłącznie do zapisywania problemów zauważonych podczas ręcznej obserwacji przejść end-to-end. Nie jest testem, konfiguracją testu ani częścią aplikacji; jego zmiany nie powinny wpływać na uruchamianie E2E.

## Zasady

-   Dopisujemy obserwację dopiero po jej zauważeniu w konkretnym przejściu E2E.
-   Nie oznaczamy problemu jako zamkniętego bez ponownego przejścia i dowodu regresji.
-   Szczegóły techniczne, logi i zrzuty zapisujemy w powiązanym raporcie lub katalogu dowodów, a tutaj utrzymujemy zwięzły indeks.
-   Statusy: `OPEN`, `REPRODUCED`, `FIXING`, `FIXED_PENDING_RETEST`, `VERIFIED_CLOSED`, `WONT_FIX`, `AWAITING_PO`, `BLOCKED`.

## Kolejność realizacji

Realizujemy wyłącznie zadania obecne w aktywnej tabeli. Zakończonych identyfikatorów nie utrzymujemy w tej kolejce; ich raporty i historia Git pozostają źródłem historii. W obrębie etapu obowiązuje kolejność od lewej do prawej. Następny etap zaczyna się po raporcie, wymaganej weryfikacji i pushu etapu poprzedniego. Nie przechodzimy dalej, gdy wymagany retest lub dowód nie istnieje.

1.  **Legal i Your data:** `ODK-E2E-104` → `ODK-E2E-090` → `ODK-E2E-105` → `ODK-E2E-106` → `ODK-E2E-107` → `ODK-E2E-108` → `ODK-E2E-109` → `ODK-E2E-110` → `ODK-E2E-111` → `ODK-E2E-112` → `ODK-E2E-055`.
2.  **Treść i konfiguracja pakietów:** `ODK-E2E-096` → `ODK-E2E-097`.
3.  **Odzyskiwanie lokalnych danych — design i wdrożenie:** `ODK-E2E-113` → `ODK-E2E-114`.

`ODK-E2E-104` jest pierwszym następnym zadaniem.

Provider/release gate’y tworzą osobną kolejkę blokującą wydanie: `ODK-E2E-082` → `ODK-E2E-083` → `ODK-E2E-084` → `ODK-E2E-085` → `ODK-E2E-086` → `ODK-E2E-087` → `ODK-E2E-088` → `ODK-E2E-099`. Uruchamiamy ją po zapewnieniu wymaganych dostępów, konfiguracji i decyzji właściciela. Brak tych warunków nie blokuje etapów produktowych powyżej.
