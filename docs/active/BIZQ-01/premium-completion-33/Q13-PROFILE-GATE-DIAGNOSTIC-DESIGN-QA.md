# Q13 profile-gate diagnostic design QA

**Verdict: PASS WITH CONDITIONS.** The plan targets the unresolved fact needed to choose a safe next step: which operation in the ordinary profile-storage gate throws, and what allowlisted error category it carries. It makes no product change and does not call a storage API from the debugger. The existing profile gate remains fail-closed.

Source inspection confirms there is no existing safe diagnostic event for this gate. `recordDevelopmentBootstrapDiagnostic` is used by `ContentPreparationGate` and later `applicationBootstrap`; `ProfileStoragePreparationGate` does not call it. The profile gate's catch projects errors to a user-facing reason and an optional closed encrypted-storage failure code. A `LocalLogoutControlError` receives a distinct message, while other errors show `LOCAL_OPERATION_FAILED`. Therefore the current screen and registry/snapshot metadata cannot identify whether the failure came from adapter creation, logout-control read, encrypted-storage preparation, or prepared-profile inspection. This matches the remaining gap in `Q13-OLD-MODULE-DIAGNOSIS.json`.

A breakpoint at the exact loaded `ProfileStoragePreparationGate` catch entry is the smallest source-faithful diagnostic if one ordinary new startup is approved. Inspect only known error class names, own allowlisted code values, and allowlisted source-relative module filenames needed to classify the stage. Do not evaluate message, raw stack, arbitrary object properties/getters, state, storage, identifiers, or native values. Resume immediately and remove the breakpoint. Keep debugger protocol output private; publish only a bounded category/stage receipt. If the breakpoint does not bind to the unique private-source gate module, or the captured value does not fit the allowlist, stop without another attempt.

One ordinary reload is still a repeat of the gate, even though it is not a manual Retry-button press or a direct function call. This is a material exception to the earlier `Q13-RELEASE-STORAGE-DIAGNOSIS.md` instruction not to retry the gate diagnostically, because a successful logout-control read may continue into `prepareProfileStorage()`. That path can create encrypted-storage keys/manifests, open or migrate storage, and inspect the profile registry. The proposed one-shot observation is justified only as a single ordinary startup after the corrected entry topology, with no Q13 trial or answer, no manual storage/bootstrap call, and a strict stop boundary. If startup reaches `ready`, compare the selected account against its known baseline before any session/profile/UI mutation. If it remains unavailable, do not take repeated storage snapshots or attempt recovery; stop after capturing the one safe error category. This does not prove the gate is non-mutating or the error caused by a particular subsystem.

The source-level success path is ordered: `createNativeLocalLogoutControl()` and `logoutControl.read()` precede `prepareProfileStorage()`, which precedes `inspectPreparedProfileState()`. `prepareProfileStorage()` can invoke the encrypted-storage bootstrap and its staged key/manifest operations. That makes the bounded attempt and post-start baseline requirement necessary; the absence of a Q13 session alone is not a data-preservation proof.
