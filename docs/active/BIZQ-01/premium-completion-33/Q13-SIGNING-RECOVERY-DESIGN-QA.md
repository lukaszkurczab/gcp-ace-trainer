# Q13 signing recovery design QA

**Verdict: PASS WITH GAPS.** The bounded signing correction is justified as an artifact-fidelity fix for the same-app simulator test, while the earlier local logout-control failure remains undiagnosed. The plan correctly does not claim that signing caused that failure. Keep the next build and any v2-to-v2 regeneration in test tooling only, and gate installation on artifact inspection.

The evidence supports two separate facts. The old Release app launched and wrote a fresh cache entry receipt, but its first local logout-control read stopped the startup gate before profile storage preparation or Q13 resume. That outcome can be either `local_logout_control_corrupt` or `local_logout_control_unavailable`; it does not implicate MMKV, the account provider, or Q13 resume. Separately, the reported signature metadata shows the Release artifact was linker-signed with a signature identifier different from the configured bundle identifier, whereas the Debug backup has the expected identifier and ad-hoc signature. Correcting that artifact mismatch is a valid test-fidelity step, but is only a hypothesis about the Keychain-visible failure.

The proposed build-script scope is appropriately narrow. `q13-build-release.mjs` currently passes `CODE_SIGNING_ALLOWED=NO`; changing the isolated driver to Xcode simulator ad-hoc signing, retaining the existing Release/simulator/architecture/environment/private-log guards, is reversible and does not require product entitlements, identity, Keychain, or storage changes. The required pre-install checks—configured `CFBundleIdentifier`, matching code-signature `Identifier`, ad-hoc Xcode signature without linker-signed flags, and successful strict signature verification—are concrete and falsifiable. Do not install any artifact that fails one of them, and do not describe a passing signature check as proof that SecureStore or Keychain is available.

The proposed v2-to-v2 recovery is also correctly separated from the previously reviewed v1 path. It should bind the prior instrumented v2 checkout to its own private five-path patch and build hashes, refuse any stale/foreign/extra/symlinked path before mutation, preserve the prior binding, restore only the two tracked sources and three generated helpers, then create a distinct fresh nonce and external v2 binding. The actual prior Release entry receipt remains evidence only for that previous build; regeneration cannot carry it forward as evidence for the corrected artifact.

On the next ordinary launch, keep the recovery interpretation bounded. If the local logout gate fails again, stop there: do not retry it as a diagnostic, clear the control record, remove app data, or bypass the gate. The separately reviewed one-read probe can distinguish corrupt from unavailable without opening profile storage if that distinction becomes necessary. If ordinary startup passes the gate and reaches normal UI, that establishes only that this run proceeded further; it does not retrospectively establish why the prior artifact failed.

## Design conditions

- Use a single existing simulator and install over the same configured bundle identity without uninstalling or clearing app data.
- Build OOD23 with a fresh v2 nonce first; verify signature and bundle metadata before install. Obtain ordinary session/entry/resume evidence before preparing OOD24 with its own fresh nonce.
- Keep every source/patch/build binding and raw build/signature diagnostic private. Public receipts remain allowlisted facts and hashes.
- Keep Q13 acceptance gated on actual OOD23 exact-resume success, OOD24 exact mismatch, preservation comparison, and ordinary UI evidence. The existing OOD23 gate failure means none of those downstream results can be presumed.

Scores: objective/architecture fit **0.94**, simplicity **0.84**, risk **0.82**, maintainability **0.86**; minimum **0.82** (threshold **0.80**). The residual risk is causal uncertainty about the earlier logout-control read and the possibility the corrected signature still does not make it available. The proposed pre-install artifact gate and stop-on-repeat-failure rule contain that risk without adding a speculative product change.

This is a design review only; no implementation, build, install, or runtime action was performed.
