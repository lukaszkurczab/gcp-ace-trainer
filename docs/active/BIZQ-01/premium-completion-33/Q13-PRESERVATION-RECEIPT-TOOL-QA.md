## Findings

- `q13-test-attestation/preservation.ts` reads only the already-published storage facade, checks account profile and inactive transition before obtaining storage, and reads key inventory and string values without a writer/bootstrap path. It fails closed on unreadable envelopes, unknown canonical keys, active-profile/session mismatches, nonzero attempts/draft responses, or an active journal. The receipt contains safe facts and SHA-256 digests rather than raw keys, IDs, answers, or values.
- The semantic projection is explicitly versioned. `semanticEnvelope` removes only top-level envelope revision, the three named active-foreground-timer fields, and session `activeForegroundMs`; canonical serialization preserves item order and associates option vectors with their occurrence. The comparator requires matching key inventory, session facts, and semantic hashes. Raw hashes remain private explanatory evidence.
- `attestation-runtime.template.txt` invokes the snapshot only from the existing exact-resume observer after the resolver settles. Its wrapper preserves the original return object or rethrows the same error, while observer/read/receipt failures remain safe and do not replace application behavior. The evidence is correctly limited to that resolver boundary; remaining resume work and UI behavior still need their separate acceptance evidence.
- `generate.mjs` validates the prior v1 source ref, source/content hashes, exactly four modified paths and each current file hash before restoring only the two source files from `git show HEAD` and deleting only the two generated helpers. It then applies a fresh v2 nonce/binding. `completed_bound` requires app-tree and embedded-JS hashes. The added `failed_no_install` and `unbuilt_no_install` branches require `buildBinding: null`; they do not synthesize build hashes or imply execution. The README now documents those outcomes and their limited claim.
- The historical-v1 compatibility correction accepts exactly one of two three-entry `toolSourceSha256` maps: `generate.mjs`, `attestation-policy.ts`, and either `attestation-runtime.template.ts` (the older binding shape) or `.txt` (the packaged shape). Both variants still require SHA-256-shaped values, exact admitted source/content identity, the exact four-file patch map, and byte hashes matching the current checkout. Extra, mixed, or omitted map keys fail the exact-key check. The generator tests exercise both historical key spellings while preserving the existing dirty-file refusal and fresh-nonce regeneration checks.
- The prior build attempt failed before an installable app/embedded bundle existed. The explicit `failed_no_install` outcome is therefore the appropriate recovery classification for that source copy; the separate never-built OOD24 copy uses `unbuilt_no_install`. Those classifications remain operator inputs, not facts inferred by the generator, so the runbook must use them only after the build process has stopped and the no-install state is established.
