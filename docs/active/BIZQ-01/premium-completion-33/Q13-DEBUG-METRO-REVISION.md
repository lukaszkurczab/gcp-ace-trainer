# Q13 Debug/Metro revision plan

## Cel

Complete Q13's OOD23→OOD24 exact-content resume contract on the existing iPhone 17 simulator, using the same installed Patternly Debug app identity and one sequentially owned smoke Metro process. Prove that the OOD23 JavaScript loads, creates one ordinary unanswered item, and resumes it under its exact catalog identity; then load the exact OOD24 source and prove the existing OOD23 session fails closed at the original exact resolver with its order and unanswered state preserved.

This revision verifies the app's real package/content contract. It does not claim an iOS binary upgrade or execution of an unmodified Release binary. All screenshots, runtime receipts, raw snapshots, environment files, account credentials, and detailed paths stay private.

## Ustalenia

The Release smoke attempt cannot exercise local smoke auth: `q13-build-release.mjs` validates `.env.smoke.local` but builds Xcode `Release`, while `readDevelopmentFirebaseAuthEmulatorOrigin()` intentionally returns no emulator address when `__DEV__` is false. `AccountSessionProvider` then requires that origin for smoke and shows the generic unavailable state before creating the auth client. The source diagnosis is recorded in [Q13-RELEASE-AUTH-DIAGNOSIS.md](Q13-RELEASE-AUTH-DIAGNOSIS.md). Do not repeat Release smoke or relax this guard.

The Q13 v2 observer already writes a fresh-nonce `js_bundle_entry` receipt with current public OOD version/hash and writes `exact_resume_success` or `identity_mismatch` only around the original `resolveRuntimeForSession` result. Its preservation observer reads only the published storage facade after checking the active profile and inactive transition; it fails closed on unclassified or invalid required data. The receipt/cache behavior has a Debug-only runtime capability PASS in [Q13-CACHE-CAPABILITY-2026-10-07-03.json](Q13-CACHE-CAPABILITY-2026-10-07-03.json).

The reviewed v2 comparator currently requires an app-tree hash and embedded-JavaScript hash. That proves a packaged app's bundle, not the JavaScript served by Metro. A Metro run therefore must not reuse a Release `buildBinding`, label the Debug app's embedded JavaScript as the executed OOD source, or claim the current comparator passed. The smallest tool change is a separate, versioned Metro-only execution receipt that links to an unchanged v2 source binding by its exact hash and nonce, records the observed Debug app identity and Metro source context, and validates the matching runtime receipt. It requires no v3 source-binding schema, no fake app/embedded-JS hash, and no change to the existing packaged-build comparator. Require independent design review and focused refusal/comparison tests before implementing this sidecar. No runtime or private evidence changes are part of this plan.

The OOD24 binding with nonce `1ccc…` is reported as `unbuilt_no_install` and never executed. Keep it immutable and use it as the source-only binding only if the current v2 tool, exact source/content/tool/patch hashes, clean checkout scope, and nonce absence all validate. Do not pass it to `regenerate`, rewrite it, or add build hashes. If it fails validation, use `apply` on a new clean exact-ref OOD24 checkout to generate a fresh source binding. For OOD23, use the existing strict v2 regeneration path from the actual signed `completed_bound` nonce `829…` binding; let it generate a fresh nonce and binding, and keep the old binding/receipt immutable. The Metro-only sidecar links each v2 source binding to its runtime receipt and separate Debug-app/Metro execution context. Confirm the resulting OOD23 nonce differs from the unused OOD24 nonce before either device run. If the old binding or checkout does not validate, stop; never hand-edit a binding or claim a nonexistent build.

The existing Debug backup uses the same bundle identifier, `com.lkurczab.patternly`. It is the sole simulator app binary for this revised test; exact source changes are served sequentially from the two private admitted-ref checkouts. The Debug backup and Release artifact remain separate evidence. A new native build, simulator, uninstall, app-data clear, RevenueCat interaction, account creation, Firestore operation, or product configuration change is outside scope.

## Verification and gates

Before any device action, the separate Metro-only tool must pass focused tests for linking unchanged v2 source bindings by exact hash, validating the fresh OOD23 regeneration binding and unused OOD24 binding, checking Metro port/CWD/app execution context, matching runtime receipt nonce/stage/catalog identity, exact preservation comparison, duplicate/reused nonce refusal, and refusal to represent Metro execution as packaged-build evidence. Keep the v2 generator, its Release comparator, and historical bindings intact. The exact-ref patch must remain limited to the existing five Q13 paths; `content-lock.json` and product/config/native/auth/storage/scoring code stay unchanged. Run the existing content integrity check for both exact refs, inspect both source bindings and the sidecars, and run the new tool's focused tests without rewriting v2 bindings.

The live run stops on an ambiguous Metro owner, missing cache receipt, source/binding mismatch, failed published-state snapshot, unexpected profile/account transition, any need to alter the current Premium test input, a required provider/RevenueCat flow, changed answer/order, or any gate other than the expected exact resolver outcome. A failed read does not justify retrying a stateful bootstrap, changing credentials/configuration, removing data, or synthesizing a PASS. The final report must call this a same-app Debug/Metro content-package acceptance run and explicitly exclude OS-binary-update and unmodified-Release claims.

Scores: objective/architecture fit **0.94**, simplicity **0.87**, risk **0.84**, maintainability **0.86**; minimum **0.84**. The route uses the repository's supported smoke/Auth Emulator boundary and an existing same-app Debug artifact. Its added tool contract links unchanged v2 source bindings to execution receipts without changing the generator or packaged-build path. Residual risks are the existing profile/auth gates and cache survival; both fail closed without new-account or data-reset fallbacks.
