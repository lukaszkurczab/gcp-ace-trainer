# Q13 Debug/Metro comparator acceptance QA

**Verdict: PASS WITH GAPS.** The new comparator is fit to gate the proposed OOD23-to-OOD24 same-app Debug/Metro run, provided its result is described as source-execution/preservation evidence and not packaged-build, Release, or OS-update evidence. It does not authorize or perform any simulator, app, account, storage, build, or Metro action.

The implementation at `q13-test-attestation/metro-compare.mjs` admits only the two approved refs and their public catalog identities. It requires source-only v2 bindings, a fresh distinct nonce per run, exact current tool/source/patched-file hash maps, and `buildBinding: null`. The contexts are explicitly `metro_debug`; they must match the binding-file digest and nonce, the same verified app bundle/signature and simulator fingerprint, and sequential single-listener/single-inspector Metro observations on `[::1]:8081`. Runtime receipts must be the exact four-stage vector: OOD23 entry plus exact-resume success, then OOD24 entry plus identity mismatch. Snapshot checks retain the one-item old pin, index/order and option digests, zero attempts/drafts, no journal, identical key inventory, and equal semantics for each required canonical category. The README accurately limits the claim and says context observations must come from the actual run; the comparator itself cannot retrospectively inspect a process, simulator, signature, or source checkout.

The privacy and failure boundaries are suitable: the CLI reads eight mode-0600 regular evidence files only from private temporary roots, emits only a safe status/category, and rejects malformed or mismatched evidence. It does not construct app-tree/embedded-JS hashes, route Metro evidence through the packaged comparator, or provide a fallback when the app/storage gate fails. Tests cover source/build binding, stale bytes and nonce, execution mode/catalog/app/device/process context, exact stage vector, order and required category preservation, and private-file permissions.

One non-blocking hardening gap remains in `validSourceBinding`: it checks `bindingBytesSha256` for truthiness rather than SHA-256 syntax. The documented `compareMetroFiles` CLI computes this value from the actual binding bytes, so the prescribed CLI path is safe; however, the exported `compareMetroEvidence` API can accept an arbitrary truthy string when the supplied context repeats that same string. Validate it with `shaText` and add a direct-API rejection test before relying on that API outside the CLI. This gap does not invalidate the proposed CLI-gated run.

Independent verification: `node --check docs/active/BIZQ-01/premium-completion-33/q13-test-attestation/metro-compare.mjs` passed; `node --import tsx --test docs/active/BIZQ-01/premium-completion-33/q13-test-attestation/metro-compare.test.mjs` passed all 6 tests. I did not run the Metro comparison against runtime receipts, inspect private receipts, or perform device/runtime actions. Parent-reported broader test/typecheck results are not claimed as independently rerun here.

The existing design review remains applicable: restore the current Debug app and account baseline independently of this sidecar; require the comparator only before OOD23/OOD24-dependent UI. The account's selected-profile baseline must match before Q13 session mutations. This acceptance does not claim the source mismatch behavior has run or passed.
