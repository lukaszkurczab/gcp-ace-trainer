# Q13 Release preservation receipt — independent design review

**Verdict: PASS WITH GAPS for the proposed test-only evidence extension.** The design is source-faithful and addresses a concrete gap: the current Release flow lacks a Metro-based before/after inspection of the persisted unanswered session and related canonical state. It does not establish Q13 runtime acceptance, and it does not authorize treating an instrumented build as an unmodified release binary.

## Assessment

The proposed read path matches the current storage contract. `getKeyValueStorage()` throws before storage is published and returns the existing `KeyValueStorage` facade after publication; `getAllKeys()` and `getString()` are reads. The proposed profile/transition guards use `getActiveStorageProfileOrNull()` and `isProfileTransitionActive()` and correctly refuse to initialize storage. The actual keys, session, attempt and draft models support the stated categories and safe facts. The known volatile fields match the recorded timer/checkpoint changes in the Q2 and common-materials receipts.

The semantic comparison is appropriately strict: every required key remains represented, additions/removals change inventory, envelopes must validate, and every payload field remains compared except top-level envelope revision and the enumerated timer/session elapsed-time fields. In particular, answer/attempt payloads, persisted draft responses, item position, item order, option order, content identity, settings, goals and plans are not projected away. An unknown canonical key or unreadable required value fails closed. Account lifecycle, Guest metadata, outbox and notification APIs remain expressly outside the claim rather than being silently treated as equal.

The hook preserves the application’s exact result/error contract: it observes the same `resolveRuntimeForSession(session)` promise used by the reviewed Q13 tool, performs no canonical writes, and contains read/serialization/cache-receipt failures. Exact old/new public catalog identities and the persisted OOD23 session pin are separate facts, which is necessary to distinguish “current catalog is v24” from “stored session still pins v23.” Safe counts and ordered digests can verify the one-item, index-zero, no-attempt/no-response fixture without exporting its IDs or answers.

Scores: objective/architecture fit **0.95**, source faithfulness **0.96**, simplicity **0.86**, risk **0.82**, maintainability **0.84**; minimum **0.82**. The remaining risk is bounded to receipt interpretation, deterministic digest formatting, and cache survival; it does not justify a different inspection mechanism or a product-code change.

## Conditions to carry into implementation

1. **Keep the stage claim exact.** The current wrapper observes `resolveRuntimeForSession(session)` inside `resumeActiveSession`, before draft retrieval and runtime validation. A preservation receipt at that point proves the stored state around the resolver boundary only. Do not label it “full resume completed”; retain ordinary UI evidence for the resumed unanswered Q1 and the fail-closed v24 mismatch as separate acceptance evidence.
2. **Version and specify the digest format.** Put an explicit snapshot/projection schema version in each preservation receipt and bind it through the instrumented source/patch hash. Specify the exact existing canonical serializer used for each semantic projection and for the ordered item/option vectors; preserve vector order and occurrence association. Never compare ambiguously joined IDs. Keep the timer exceptions path-specific and test that arbitrary non-timer changes reject equality.
3. **Bind each receipt to its own build.** v23 and v24 are separate instrumented artifacts and should have separate fresh nonces. Verify each receipt nonce, current catalog identity, source/patch/build binding and expected stage against that same artifact’s private binding; do not require nonce equality across the two releases. Ensure each exact-nonce receipt path is absent before its run. A missing, malformed, stale, or unbound receipt means no preservation PASS.
4. **Treat hashes as private evidence.** Hashes avoid emitting raw IDs, keys, answers, settings or profile data, but stable hashes can still be linkable or dictionary-tested. Keep both receipts and host-side comparison output private; emit only safe status/category results. Do not add raw values or per-record key names to console output.
5. **Fail closed if the baseline cache receipt disappears.** The approved runtime receipt location is app cache, which may be purged across an install. The proposal already says missing receipt blocks comparison; preserve that rule and do not reconstruct the old snapshot from a new-build read or fall back to a storage mutation/debugger.

The proposed one-item active OOD session, index zero, zero attempts and zero draft responses are the right required facts for this fixture. The acceptance comparator must confirm those facts in both receipts and verify equal ordered digests and required-category semantic hashes; it must not use aggregate counts alone to claim answer/order preservation. Run the proposed pure tests for volatile-path precision, key inventory additions/removals, unclassified keys, unpublished/transition-active refusal, deterministic order digests, and original result/error identity on read/write failure before relying on the new receipt.

## Scope boundary

This is a design review only. The existing Q13 tool QA reported 10/10 tests and a Debug-only cache capability probe; neither is Release preservation evidence. The patch-generator’s external binding and separate build/bundle-identity checks remain required. No build, install, device action, receipt creation, or account/storage inspection was performed for this review.
