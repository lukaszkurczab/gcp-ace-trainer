## Findings from the nine current units

I read the current whole objects across all 162 IDs, including prompt, all four constraints, every option, answer, Reason, all five Details fields, all option-level messages, and source references. Each prompt explicitly names its unit’s “interview lens,” then appends one of a small set of generic review constraints. That title signal is not treated as a defect by itself: the spec allows named techniques where diagnosis and transfer remain meaningful. The problem is that the accompanying facts do not establish the chosen technique or make the nearest alternatives fail.

Across all 162 objects, the keyed option ID is `owner_preserves_contract`; the same four wrong-option IDs and nearly identical texts recur in every unit: export state to a coordinator, inherit for reuse despite contract change, expose representation, or add speculative registry/event indirection. The keyed mechanism changes only by unit title, then repeats a quoted scenario invariant “inside the owner.” The scenario is usually about a domain invariant (such as non-overlapping meter reservations, consent before disclosure, or idempotent payout), not about the relevant interface, subtype, type-parameter, extension, or base-class decision. In particular, `ood-n04-b02-i013` says only that payout release is idempotent and tied to a settled order; it states no subtype family, shared substitutable contract, or dispatch point. The package18 semantic sample reached the same finding for that exact current file hash and item fingerprint.

The supporting explanation does not close the gap. In every unit, `errorCorrection` and `transfer` are byte-identical across its 18 items; the messages for `representation_leaks` and `speculative_indirection` are also identical in all 162. The coordinator feedback is filled from a generic lens/constraint template and is grammatically malformed (“It moves [lens] is the primary decision…”). `Reason` starts with the keyed generic mechanism instead of orienting from the decisive case fact; `scenarioApplication` and the constraint-driven `boundaryOrTradeoff` repeat the template’s broad owner language. The same six generic Java/.NET/TypeScript/DDD references recur on every item, whether or not the scenario states any corresponding language or framework. These are current source observations, not claims about renderer display order.

The distinct objective in each unit cannot be inferred from the story-only facts. For example, the B02 payout case cannot select polymorphism over a direct operation; B07 notarization merely says the seal covers an immutable revision, without a generic type or variance requirement; B08 clinic-referral consent says nothing about a caller’s capability set; and B09 subscription bundle pricing says nothing about common implementation across substitutable subclasses. The other scenarios repeat the same mismatch with different nouns. This creates an answerable “choose the generic owner/contract maxim” exercise but not the declared mental-model decision, and the common caricatures do not teach plausible alternatives or their decision boundaries. This directly conflicts with BIZQ-01 §§4.1, 4.3, and 4.4 and the content guidance requiring item-specific Reason/Details and meaningful distractor explanations.

## Smallest coherent next package

Use one fixed manifest for the current nine arrays and 162 whole objects. Before authoring, lock the package contract to the existing BIZQ-01 and docs07 rules: keep unit/node/type/scoring/counts; retain an item ID for a correction that preserves its primary decision and reserve a new ID for an actual changed decision; do not presume every row needs a new identity. Give each question its unit-specific objective and visible facts, a defensible nearest alternative, and matching Reason/Details/option feedback. Compare the authored decisions with the accepted N01/N02 controls and the corrected N03 cohort, and assess each B02–B09 target against its named concept rather than adopting another all-purpose owner template. Reuse official technical references only where the answer depends on a language/framework claim; scenario stipulations are not universal guarantees.

The package should include a current-source exact manifest, independent whole-object review before activation, and only then the existing producer proof → generated artifact → consumer/admission sequence. Structural scoring/reversal checks and source preservation are separate from semantic acceptance. No finding here supports a schema change, new runtime rule, widened pool, selector/native/Premium claim, or any release-policy change. Full N04 replacement is justified by the same confirmed defect appearing in every unit—not by the number of questions or a requirement that every row express a unique concept.
