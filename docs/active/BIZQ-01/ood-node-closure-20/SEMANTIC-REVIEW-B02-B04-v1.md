## Blocking correction

**B03-i033 — failure behavior is unstated, so the key is not the only compatible choice.** The prompt says `Accepted(offset)` means the entire chunk is stored at that offset. It does not specify any required result for a chunk that cannot be fully stored. The keyed option (“Return Accepted only when the full chunk is stored”) follows the stated success postcondition. But option D (“Throw an unchecked memory exception for large chunks instead of returning the upload contract’s retryable failure”) may also preserve that postcondition: the prompt never promises a retryable failure result or forbids an exception. The error-correction Details then asserts that such a retryable outcome is “the shared recovery outcome,” adding a premise that the learner was not given.

This violates §4.1 of the existing BIZQ-01 question-quality contract: single choice must have one answer under the visible facts, and a decisive assumption cannot first appear in Details. It also violates §4.4’s requirement that Details explain the scenario without adding an unsupported premise. The smallest correction is to make the failure contract visible and keyed—for example, state that `append` returns either `Accepted(offset)` or `RetryableFailure`, that failed chunks remain retryable, and that exceptions are not part of the contract—or change option D so it is wrong under the current stem without relying on an unstated failure policy. Keep the stable item ID if the primary decision remains “do not report full acceptance for partial storage.”
