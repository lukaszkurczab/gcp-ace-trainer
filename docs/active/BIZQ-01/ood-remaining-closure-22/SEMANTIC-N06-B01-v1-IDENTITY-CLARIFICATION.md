## Identity criterion

The controlling text is the canonical [Stable item and interaction identity](../../../../docs/07-content-guidelines.md#stable-item-and-interaction-identity) clause: keep an ID for corrections to facts, ambiguity, a wrong accepted answer, incomplete explanation, weak distractors, or omitted constraints only while the primary instructional intent and taxonomy remain the same; use a new ID when the primary skill, mental unit, problem archetype, core answer semantics, or trained decision materially changes. N06's accepted cohort clause applies that same test and explicitly says not to infer identity from the unit label or reserve new IDs as a quota.

I compared each entire before/current object. The former prompts do contain distinct business operations and invariants that the new scenarios do not preserve literally. For example, old `i001` asks about a notary sealing the exact immutable document revision; new `i001` asks where a district-specific rate algorithm belongs in a stable statement workflow. Old `i002` discusses idempotent release tied to a settled order; new `i002` concerns regional eligibility algorithms in a shared claims sequence. Old `i017` requires badge revocation to be visible before an access decision; new `i017` asks where contract-specific labor estimation varies in a common work-order flow. These old invariants are not asserted as facts in the new vignettes, and I do not claim they are preserved.

Those old operations were contextual material attached to an explicit Strategy exercise, rather than a different accepted archetype. Each entire old prompt tells the learner to apply the “Strategy, policy objects, and interchangeable behavior” lens; each accepted option has the same operative decision: inject an interchangeable policy when behavior varies independently of a stable workflow. The old `Reason` repeats that decision. The old `scenarioApplication` and `Details` then claim the unrelated invariant is kept with an owner, but the prompt supplies no independent algorithm variation or mechanism linking that invariant to Strategy. That is the diagnosed factual/causal defect: the keyed Strategy choice has no visible Strategy trigger, while the added context and explanation are unsupported. The new questions repair that defect by making the variable algorithm, its selector, and the stable surrounding process explicit. Their keyed action remains “place the changing algorithm behind a common policy operation and keep the caller's workflow stable.”

On that full-object comparison, I classify the domain and invariant replacement as correction of the unsupported scenario application, not a change of primary skill/archetype. The previous item already explicitly names Strategy and keys the same Strategy decision; the current learner still decides where one selected algorithm belongs relative to its stable workflow. The taxonomy remains `OOD-N06-B01`, and the interaction remains single-choice. I therefore retain the existing question IDs. This is a bounded semantic judgment about the frozen objects, not an answer derived from the shared mental-unit name alone. All correct-option text and meanings changed and correctly use fresh option IDs; no old option ID is reused.

## Options and cross-unit check

The proposed correct answers are case-specific applications of that same strategy boundary. The recurring alternatives—branch in the stable workflow, duplicate the workflow for each algorithm, delegate computation to callers, or model executable behavior as data/global mutable selection—are recognizable competing designs. Their feedback refers to the actual selected domain behavior and the stated change boundary. The repeated family is appropriate practice for one Strategy mental unit; I found no evidence that the choices can be selected by a purely stylistic cue. The “global mutable selector” distractor describes the well-known risk of crossing per-account/per-request selections; the examples concern services with multiple customers, plans, regions, purchases, or concurrent work. This is not a newly imposed concurrency requirement.

The nearest accepted N01–N05 neighbor is the N05-B07 Bridge objective: it separates two independent axes (for example, policy from transport) that must work in combination. B01 asks a different decision: where to put a single variable algorithm while keeping one workflow stable. N01/N02 examples about policy ownership, adapters, state, or accepted outcomes likewise do not train this same calculation-placement decision. No cross-unit duplicate was found.
