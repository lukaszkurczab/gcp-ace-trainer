# BIZQ-01 Premium profile and OOD reachability preflight

Date: 2026-10-05. This is a read-only inspection. It did not create an account/profile, change settings or environment, start a service, or operate a device.

## Finding

The Settings Premium switch and a local smoke Premium test profile are different mechanisms. The switch only makes the smoke build's single AWS package fixture visible; it does not bypass authenticated Premium admission for Design Interview sessions. Source code has a local backend fixture that can return an active entitlement to an authenticated emulator account, but the current API process's selected fixture state is unknown. A local test-profile route is usable only if the already-running API is configured with the active fixture; this read-only preflight does not propose changing that setting, starting or restarting services, or creating the account. Any entitlement from that fixture is simulated, not RevenueCat/provider evidence or a production Premium profile.

That route reaches only the bundled OOD N01 node. Every normal OOD Design practice mode selects N01; all Design modes require Premium admission. N08/N09 are not selected by those modes, and no OOD node-package offer exists in the current offer map. The Design Interview Simulation is also Premium-gated, but it is a four-stage open-response exercise, not a sampler over the N01–N09 bank. I found no `KnowledgeCheck` question-bank route in the current implementation.

The direct PO receipt [PO-DECISIONS-2026-10-05.json](PO-DECISIONS-2026-10-05.json) authorizes preparing a Premium test profile or using the existing Settings switch, with no production purchase. It also sets the partial-answer scoring and summary behavior. The authorization does not establish that the current API uses an active fixture. The Settings switch by itself cannot provide Design session admission.

## Current paths

**Settings switch.** `premiumTestingRepository.ts` saves a device-local test key only in sandbox/smoke. `premiumNodeOfferAccess.ts` requires both the smoke runtime and that key for a `local_smoke_fixture` offer. Metro selects `premiumNodeOffers.smoke.ts` only for smoke. That file has exactly one AWS offer, `aud04_local_smoke_fixture`, containing one `choice_single` question. The production/sandbox offer file is empty. Neither this switch nor this offer exercises OOD.

**Local test profile.** `patternly-backend/scripts/localSmoke.ts` defines Auth/Firestore emulator endpoints at localhost ports 19099/18081 and the local API at 8080. `dev-smoke.ts` uses a deterministic local entitlement reader; source defaults to `expired`, and `active` is selected by the non-secret enum `PATTERNLY_LOCAL_SMOKE_ENTITLEMENT_STATE=active`. The reader does not contact RevenueCat. These source defaults do not prove the state of the already-running API. Root may inspect only that selected enum from the existing process environment, without printing the full environment; until then the live state remains unverified. No environment, service, or API state was changed in this preflight. The mobile smoke runtime connects Firebase Auth to the emulator and the API to the configured local origin. The app's existing account registration/sign-in flow can establish the authenticated test identity; the API's normal `/v1/entitlements` route returns the configured reader's fixture when reached through the app's authenticated client. This route is viable only if the existing app bundle and already-running local services are configured together with the active fixture. No current endpoint health, emulator state, credentials, or environment values were inspected here.

If the current app state is a guest with an accepted plan, use the ordinary in-app account-registration/guest-adoption flow for that local test identity; do not clear/reset storage or create a new goal. Registration marks guest installation adoption pending, and account profile preparation goes through the existing adoption flow (whose initial choice is transfer and may present conflicts for user resolution). The exact accepted plan should be checked in the normal app view after that transition. This note does not perform or certify the transition.

**Normal OOD question route.** `productModeConfig.ts` selects `requirements_use_cases_domain_vocabulary_and_model_boundaries` (N01) for each of the three ordinary OOD Design modes: `design-interview-learn-framework`, `design-interview-tradeoff-practice`, and `design-interview-weak-area-review`. `PracticeHubScreen` calls `authorizePremiumSessionStart()` before opening a Design mode. That gate uses the authenticated account's current cached/fresh entitlement; the Settings test key is not consulted by it. With an authorized local smoke test account, the native path is Practice → the existing OOD track → Learn framework or Tradeoff practice → request a supported length. N01 is bundled, so this route does not install a node package. Keep the existing track/goal and plan intact. The session selector chooses from N01; there is no exact-question picker guaranteeing `ood-n01-b01-i021` in a one-question run.

The current generated OOD artifact contains 1,413 questions and all nine nodes use `choice_single`. N01 contains 136 questions; `ood-n01-b01-i021` has the longest option at 226 characters. This establishes that a long single-choice OOD item is in the eligible N01 pool, not that a randomly selected session has displayed that particular item. It also means no OOD question can demonstrate a partial multi-select response.

**OOD Simulation.** The bundled `design-interview-simulation` profile describes a four-stage text-response scenario and uses a self-assessment reference rubric. The simulation facade creates one profile-bound occurrence and stages; it does not sample canonical question-bank items. All Design Interview modes, including this simulation, require account-backed or local-smoke test admission. Thus the simulation cannot stand in for N08/N09 question presentation.

## Partial-answer reachability

The current BESD and OOD generated artifacts are entirely `choice_single`. The current Coding N01 free node contains `choice_multiple`, ordering, and complexity questions; FESD N01 contains ordering and decision-matrix questions. Those show that other existing modes support non-single-choice interaction types. This preflight did not bind any such exact ID to an accepted, repaired BIZQ-01 item, so it cannot count one as the spec's partial-on-a-repaired-question example. The current OOD repaired set has no partial-capable item. If the criterion requires a partial response on repaired content, the exact repaired item must first be shown to be naturally eligible in an existing mode; do not alter question type, force a seed, or count unrelated content.

The PO decision is: a partial answer contributes no positive overall-score points, while preserving the `partial` diagnostic and “partly correct” summary label. The scoring change is handled separately; this preflight did not edit or test scoring.

## Feasible scope and limits

If the already-running local smoke API is confirmed to use the active fixture, emulator-backed registration is an available no-purchase route for the Premium gate and bundled OOD N01. If it is not active, this preflight does not authorize changing the reader setting or restarting the API. Any such session must be labeled a local test profile, not provider verification. The Settings switch is useful only for the AWS smoke package installation path; no OOD activation was attempted, and it is not evidence that OOD admission failed.

This profile does not create an OOD N08/N09 offer or a mode that selects those nodes. Reaching repaired N08/N09 through the runner would require an existing supported content-offer/mode path; none was found in this build. No production purchase/service setup is proposed. The practical next native step is to use the local test profile for N01 presentation, preserve the existing accepted plan through normal guest adoption, and keep N08/N09 Premium question presentation as a separate reachability gap.

No claim is made for RevenueCat/provider validation, an already-running emulator, successful profile creation, a particular N01 item being selected, N08/N09 native question interaction, repaired-question partial scoring, or full BIZQ-01 acceptance.
