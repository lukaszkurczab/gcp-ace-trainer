# BIZQ-01 guest removal 34 — independent design review

**Verdict: PASS WITH CONDITIONS** for a narrowly scoped, one-time removal of the exact original modern Guest profile and its local data. The user explicitly changed the requirement to remove that Guest; this supersedes the earlier preservation decision. The nine account profiles, their progress/settings, unrelated logout controls, and all app-global storage remain protected. No deletion, simulator action, runtime probe, or product-code change was performed for this review.

## Repository evidence

- `src/infrastructure/storage/profileStorageRouter.ts:7-10,160-188` defines two SecureStore registry slots (`patternly.profile-root.v1.a/b`), the modern per-profile MMKV prefix (`patternly:profile:v1:<id>:`), and selection methods. The router exposes `selectGuest`, `selectExistingGuest`, and `selectAccount`, but no profile-removal operation. `selectGuest` reuses an existing selected/sole Guest, so it cannot by itself create a replacement while the original Guest remains registered.
- `src/infrastructure/storage/profileStorageRouter.ts:363-374` commits one checksummed registry generation to the alternate SecureStore slot and reads it back. A single commit therefore leaves an older valid registry copy in the other slot. Deleting the old profile prefix after just one registry commit would leave a stale registry copy that still references the removed ID.
- `src/infrastructure/storage/encryptedStorageNative.ts:39-55` opens one shared MMKV base and maps the `KeyValueStorage.remove` operation to MMKV key removal. The encrypted-store slots are whole-app stores, not per-profile stores. `src/infrastructure/storage/encryptedStorageBootstrap.ts:381-383` confirms `removeUnavailableEncryptedStorage()` deletes the legacy store, both encrypted stores, and all manifests/keys; it is not a profile-deletion mechanism.
- `src/features/home/localReset.ts:3-27` clears learning history. `src/application/learningMutations/localReset.test.ts:63-76` explicitly verifies that this operation preserves the Guest installation and local dataset identity. It cannot meet the new request to revoke the Guest profile itself.
- The current public Guest receipts bind the original Guest dataset ID hash to `b880a3a8d1530601f6f1ed2f244078468f09f51f9d68ba5f6d3cec95cfa5e52d`, with installation ID hash `498a8a5cbc36ed6331567374098786cc922f8133a4afceb7471ca0d77b4de760`. The profile kind, exact runtime registry, and raw local ID must still be checked in a fresh preflight before any mutation; these receipt hashes alone do not authorize selecting a raw ID.

## Design decision

Use one temporary, infrastructure-owned router operation that accepts the expected Guest ID hash, verifies the exact current profile, creates a fresh Guest, selects it, removes the old Guest from **both** registry slots, then deletes only the old modern profile prefix. Do not add a generally available “delete profile” UI/API for this one requested cleanup. Do not implement this with direct app-data clearing, `clearAll`, a whole-store reset, an unscoped MMKV script, or by changing the registry outside the canonical router.

This is a new narrow router lifecycle capability because no existing route can remove a profile. It must remain internal to the reviewed task operation; no new user-facing product surface is needed. Add a durable, validated removal journal in the existing SecureStore control plane. The journal records the exact target and replacement IDs, expected hashes, operation stage, and version. A boot/preparation guard must refuse to publish any profile while this journal is pending, with an explicit recoverable state. This is transaction recovery for a concrete cross-store crash window, not a new access preference or provider gate.

The operation order is:

1. Enter the global profile-transition barrier, stop timer/session callbacks and other writers, drain or recover pending local mutation work, close published scoped storage, and confirm no active learning journal remains. Do not proceed if a write/recovery is uncertain.
2. Open the normal encrypted base and both registry slots. Fail closed on bootstrap errors, invalid checksums, duplicate/conflicting registries, or a missing/corrupt slot. Require exactly one target whose registry kind is modern `guest`, whose ID hash matches the expected hash, and whose guest marker has the expected installation hash, `bindingState: guest`, and `accountId: null`. Stop if it is `legacy_guest`, account-bound, absent, ambiguous, or otherwise different.
3. Capture a private categorized baseline: both registry generations and the full account entries; key names and per-value hashes for all nine account scopes; app-global MMKV keys/value hashes; Guest and account profile categories (learning/progress, settings, active session/draft/journal/timers, lifecycle markers, and cache/download references); and the five unrelated pending logout pairs. Never publish raw values.
4. Persist and read back the removal journal before writing the replacement profile. Create fresh unique Guest installation/dataset IDs, write and verify only the replacement Guest installation/access markers, and construct a checksummed registry that selects this replacement, preserves all nine account entries exactly, and omits the original Guest.
5. Commit that registry through the canonical router and reopen/verify it. Commit the same profile membership/selection at the next generation so both SecureStore slots no longer contain the original Guest. Read both slots and verify the target is absent from each, the fresh Guest is selected, and the nine account entries are unchanged. The old Guest keys must remain untouched until this verification passes.
6. Remove only keys whose physical name begins with the exact modern prefix `patternly:profile:v1:<verified-target-id>:` using the shared base adapter. Read back that exact prefix and require zero remaining keys. Do not touch the `patternly:` legacy namespace, either encrypted MMKV store, SecureStore encryption keys/manifests, any other profile prefix, Auth, backend, Firestore, or logout-control namespace.
7. Compare the post-state against the baseline: original registry ID and every old Guest key are absent; replacement Guest is valid and selected; all nine account key inventories and value hashes, app-global entries, and unrelated logout controls match exactly. Clear the journal only after this verification. Then reopen the ordinary app and confirm the new Guest path. Keep only nonsecret receipts and private evidence hashes.

If any step fails, do not continue to delete. Before registry replacement, leave the original Guest and all data intact. After the first successful registry commit, keep the journal, keep the profile barrier active, and recover the same operation before ordinary profile publication; do not invent a new target or reselect the old Guest. Partial key removal is idempotently resumable by the journaled exact prefix. A wrong target hash, legacy profile, unexpected profile count, pending journal, unreadable registry, or mismatch in protected baseline is a hard stop.

## Capability and verification gates

Before the destructive operation, do one small real Debug capability probe through the app's already initialized native storage adapter: create a single nonce-bearing canary key in an otherwise unregistered random profile namespace, enumerate it, read the exact value, remove it, and verify it is absent. The current public facade does not expose the shared base, so use a temporary, infrastructure-owned one-shot probe that returns only success/failure and safe hashes; do not add a general raw-base accessor or UI. Compare protected account and global key/value hashes before and after. Always attempt canary cleanup; any cleanup/readback failure stops the deletion plan. This verifies the actual MMKV adapter's `getAllKeys`/`remove` behavior without touching the target or an account. Existing in-memory tests are useful for modeled ordering/fault behavior but do not replace this native probe.

Tests for the implementation must cover exact-hash and modern-Guest guards, no writes on a wrong/ambiguous/legacy target, protected profile preservation, both registry-slot updates, registry and key-removal failures at every boundary, restart/resume from each journal stage, concurrent-writer refusal, and idempotent completion. Then require one real ordinary Debug execution on the existing iPhone 17 with a fresh private baseline, the capability probe, and post-state receipts. Do not clear app data or reinstall; do not read or mutate server data.

The scores assume the two-slot registry cleanup and resumable journal above are implemented. Risk is the limiting score because SecureStore registry commits and MMKV key deletion are separate durable stores. A single generation update or an unjournaled prefix loop would fall below the acceptance threshold and is not approved. This review approves the design direction, not implementation readiness or runtime deletion.
