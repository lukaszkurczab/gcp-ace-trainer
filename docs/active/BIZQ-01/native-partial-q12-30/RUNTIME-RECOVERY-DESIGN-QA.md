The original raw files `/private/tmp/bizq30-before.json` and `/private/tmp/bizq29-after-gcp.json` are gone. The corrected brief does not pretend to recreate them. It binds the actual pre-UI snapshot output that survived in the tool transcript: `recordsSha256=1a65e6a09ecd71e259eb1ca95054a4624b2c12d1ea21ee0b720e9031638f9667`, with 81 captured records and 84 keys. I independently checked the committed `snapshot-canonical-state.mjs` algorithm: it hashes the sorted captured record keys and their raw values, while replacing account-lifecycle payloads with the limited `{revision,status,payloadFields}` projection. A fresh capture can therefore be compared to that receipt without recovering or fabricating either deleted file.

The corrected sequence is coherent: restore the existing local Auth/Firestore emulator and smoke API on their established loopback ports using the existing project/configuration; do not bypass the Auth or API readiness probes; relaunch only the existing Metro on port 8081; then take a fresh read-only snapshot before any Q12 UI interaction. Stop if its record hash, counts, category inventory, notification state, or Guest/lifecycle fences differ from the surviving baseline. Compare the post-Q12 snapshot to the new pre-UI snapshot. This validates the 79 raw records and two limited lifecycle projections, while explicitly excluding the three unread profile-metadata values and avoiding a whole-store claim. It also reuses the previously verified exact GCP progress payloads, goal/plan/settings, completed-session evidence, and unchanged lifecycle markers; it does not infer preservation from category counts alone.

The source review supports the operating boundaries. `patternly-backend/firebase.json` binds the existing Auth and Firestore emulators to loopback; `dev-smoke.ts` uses an expired local entitlement and disables SMTP and remote RevenueCat; and `runLocalProfile.mjs` requires the Auth emulator and API `/ready` checks before Metro starts. The previous attempt stopped at the Auth readiness check, so retrying only after the local emulator is ready is the correct next action. Guest startup does not authorize account recovery or marker cleanup. Existing failed/pending redacted lifecycle markers must remain byte-equivalent under the snapshot projection; stop on an unexpected account, recovery, or profile-transition UI. The smoke secrets file is present with mode `0600`; I did not inspect or print its contents.

The brief already names the intended ports and project; this is a path clarification, not a new gate. The referenced `ROOT-RUNTIME-RECOVERY-ACCEPTANCE.json` is a future receipt, not evidence that recovery has already run; the existing `ROOT-PLAN-ACCEPTANCE.json` and checksum receipt are the evidence used for this review.
