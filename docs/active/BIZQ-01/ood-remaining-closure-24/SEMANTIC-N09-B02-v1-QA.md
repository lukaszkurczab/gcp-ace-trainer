# Independent semantic review: N09-B02 v1

**Verdict: REVISE.** The 18 cases are recognizable applications of the stated testability objective: make instance inputs explicit so tests can control time, policy, identifiers, history, actor context, or collaborators. The matching question IDs are justified; each new accepted option ID represents the case-specific input choice replacing the old generic answer. Two cohort-level defects remain: every item includes a literal `undefined` constraint, and the generated feedback contains repeated ungrammatical construction sentences. The keyed choices also repeatedly provide the only complete per-instance input recipe, while alternatives are often shorter workarounds. This creates a meaningful §4.3 form cue in context; it is not a count-based gate.

## Findings

The concrete decision in each scenario is supported: tests should control the relevant construction-time value rather than read a live clock/catalog/session, mutate process-wide state, patch a finished object, or stub away the construction path. The cases vary across controlled time, regional policy, ID generation, approval history, actor context, immutable revisions, consent/sender collaborators, and time zones. This is valid transfer practice, not a need for 18 unique concepts. The selected question IDs continue the same unit objective, “Assemble testable objects with explicit construction inputs and controlled clocks, randomness, I/O, or collaborators.” The new, specific keyed answers appropriately use new option IDs.

However, all 18 `constraints` contain the literal string “The test must not use the live undefined.” It does not identify a defined dependency or a case fact. That placeholder is not a usable constraint. Feedback has the same generated wording throughout, including “while the real assembling a [object] applies the rule” and “The test runs constructing/assembling [object] with those values.” These are grammatically broken and do not explain the construction path. Rewrite the affected constraints to name the excluded source (or remove the redundant constraint) and make each mechanism/scenario explanation grammatical and specific.

The option sets also present a qualitative form cue. Sixteen keyed choices are strictly longer than every wrong choice. Across items the key is repeatedly phrased as “Pass/Supply/Provide/Require [dependency] into assembly,” directly mirroring the stem’s question about which input should be explicit. The distractors often reduce to an obvious stub, process-wide state, live dependency, or post-construction patch, while the accepted choice alone specifies an instance-controlled construction route. Those are real testing mistakes, but the repeated shape makes the intended answer recognizable before comparing the distinct scenario boundary. Keep the correct per-instance decision, but make the nearest alternatives credible competing construction/test strategies with clear case-specific failure reasons. Do not pad choices or impose a length or option-count target.
