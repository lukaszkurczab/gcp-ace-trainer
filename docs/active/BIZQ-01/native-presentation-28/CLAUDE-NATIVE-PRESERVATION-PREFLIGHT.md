# Claude partial native route: GCP preservation preflight

Date: 2026-10-05. Bounded source and prior-evidence review only. No device, local account data, reminder state, active track, service or app state was read or changed here.

## Finding

The source-level route is possible, but selecting Claude is a real track and reminder-source transition, not a read-only way to open its ordinary practice flow. The active-track selector persists Claude before it reconciles reminders. The selected track's goal and plan are stored separately from GCP's, so that transition does not itself write the GCP goal or accepted-plan records. The reminder settings are a single active-source record, however, and reconciliation immediately resolves the currently active track.

If Claude has no valid reminder source, the normal transition can cancel recorded app reminder IDs and clear the saved reminder identity and slots. If Claude has a valid source and reminders are enabled, it can schedule/recover Claude-bound reminders and cancel obsolete GCP-bound IDs. Switching back to GCP can reconcile its still-valid goal/accepted plan and recreate the same day/time slots, but the source does not guarantee the same native notification IDs. Therefore the existing route can preserve GCP goal/accepted-plan data while temporarily rebinding reminder delivery; it cannot promise continuous GCP reminder binding throughout the Claude session. Whether that is acceptable depends on the actual current GCP/Claude reminder records and must be checked by the device owner before any switch.

The existing Claude memory probe establishes an ordinary path to partial-capable questions: from empty history, complete the first normal 40-question Focus Practice session, then start the normal follow-on session. Its actual attempt objects caused the next 10-, 20-, and 40-question preparations to include all six multiple-choice transfer items. This remains a runtime-feasibility result, not native evidence, and actual device history can change selection. On device, use the question the normal prepared session actually presents; do not replace a planned item or manufacture attempt history.

## Live-read capability check

The repository has synchronous per-record readers, but no stable host-callable native snapshot/export command or app bridge. `readCanonicalEnvelope` in `src/storage/repositories/canonicalRecordCodec.ts` reads through the currently published app storage client; `readActiveTrackId`, `readGoalSnapshot`, and `getLearningPlanSnapshot` are repository functions, not a device-shell interface. The only prepared-profile inspection export, `inspectPreparedProfileState`, reports the profile registry and selected profile; it does not publish profile-scoped goal, plan, learning, or reminder records. The test storage adapters and repository tests run in Node, not against the installed device profile.

This distinction matters because production storage is encrypted MMKV. Its key is generated in-app and stored through iOS Keychain-backed SecureStore; the MMKV wrapper opens it with AES-256. The repository contains no MMKV filesystem parser or supported key export. The privacy boundary also excludes the iOS MMKV directory from backup. Do not attempt to read database files or extract key material as a substitute for an app-level snapshot.

The existing development deep-link commands are not a read probe: `audit/reset-learning-state` clears learning data and `audit/clock/advance` changes the audit clock. The local-profile scripts start the app or check backend readiness; Maestro flows drive UI but do not invoke repository readers or export storage. There is no stable product Hermes/native snapshot bridge. Thus a supported product interface does not provide one safe operation returning the full pre-switch record set listed above. Reminder Settings refresh is not safe for baseline capture because it reconciles.
