Date: 2026-10-05. This is a read-only feasibility assessment, not native acceptance, a plan/status change, or a device run. Root remains the sole operator of the existing iPhone 17 simulator.

## Finding

Q12 has a bounded, low-risk native presentation check available on the existing iPhone 17. The app already exposes saved light/dark appearance preferences, and the installed simulator tool supports querying and changing appearance and content size. A controlled pass can temporarily set only the simulator appearance and content-size category, inspect a real session’s question/options and expanded Details, then restore the recorded original simulator settings. Root’s read-only simulator query observed `appearance=dark` and `content_size=large`; native25 recorded the app preference as `System`. Preserve the app preference at System so the actual simulator appearance drives the theme; there is no need to persist app-level light/dark preferences for this probe. No additional simulator, purchase, profile, service configuration, or app data reset is needed. This establishes actual presentation only for the content and session actually visible; the prior GCP session has moderately short choices and is not evidence for a long-option repaired question.

Full Q12 remains incomplete until the same actual runner shows a currently reachable repaired question with long options and expanded Details at both themes and large system text. The current native evidence does not establish that combination. The ordinary N01 pools and the pending real Premium profile constrain which repaired OOD items can be entered through a legitimate session. Do not use a local Premium smoke fixture or audit deep-link fixture as a substitute for that session.

Q13 is not currently end-to-end feasible under the stated constraints. The source has two relevant, correctly distinct identity behaviors: a bundled-track content version or artifact mismatch blocks resume; installed node-package updates retain exact old package identities so an old reference can still resolve. Source tests cover these behaviors with real application classes, but the package installer’s native route is an authenticated Premium node offer. No real Premium profile is confirmed, and the visible install control lives in pre-session Practice Setup. Existing Maestro tooling terminates/relaunches the app and runs a learning-state reset flow, so it cannot prove an update during an active native session without changing the test conditions. A local smoke offer would establish only the fixture path. Keep Q13 as an evidence gap until an authorized real offer/profile and a natural update/resume route are available; do not infer a defect or change the mismatch policy from the missing native run.

## Q13 evidence boundary

The existing contract in docs/17 requires exact track/family/mode/content and session-plan resolution on resume. A content/profile mismatch blocks resume; the app must not map old items to current ones, resume a subset, or silently start a replacement. The current canonical runtime compares the session’s content version and artifact hash to the resolved runtime. `nodeContentPackage.installNodePackage` verifies transport and artifact identity, writes an immutable package, activates its pointer, and keeps older identities available through the package owner. `nodeContentPackage.test.ts` exercises an in-memory store; `bizq01CodingSourceCopy.test.ts` exercises current Coding resume rejection for altered version/hash. Neither demonstrates the native app while a package changes.

There is no legitimate no-profile substitute in the current evidence. `installPremiumNodeOffer` obtains an offer and profile-scoped store, and the only visible caller is Practice Setup before session preparation. The session coordinator callback checks authenticated account-generation continuity; it is not a UI-accessible “update while practising” route. A future real Q13 pass should use the already supported update route on an authorized existing account only if that profile/offer is available, retain the exact pre-update session identity, perform the real package activation through its natural UI/API route, then background/foreground and observe the actual contract: the session either resumes with the exact referenced old artifact or visibly blocks on mismatch. It must never display replacement content under the old session. Do not manufacture the profile, bypass entitlement, or edit service configuration to make this path reachable.

If the only available update is a new bundled app/content release, treat it as the bundled mismatch case: verify the ordinary version-mismatch block in the actual app rather than claiming the node-package retention behavior. A source-only test or Dev Client reload is not proof of a natural end-user package update while the native session remains active.
