## Blocking findings

1. **Systematic length cue affects all 18 keyed options (§4.3).** In every object the correct option is strictly longer than all four distractors. This is not a word-count threshold or a demand for equal-length options: it is a direct, repeated “longest is correct” signal, which the existing guideline specifically says to remove. A learner can exploit it without using the case facts. Rewrite the nearest wrong alternatives as complete, credible competing policies that fail on a named case boundary, rather than padding them. Keep the correct repository contract and its meaning stable; update diagnostics only where an alternative’s meaning changes. No prose quota or zero-warning rule is being added.

2. **B01-i002 does not rule out an adequate full-load alternative (§4.1).** The stem asks for open cases for a team and says ownership and history are stored separately. Its fourth distractor says to load every conversation and filter by team in the domain layer. That can satisfy the stated query and mapping boundary for a small bounded set; neither scale nor a requirement to push the predicate to storage is visible. The explanation calls the work “unbounded,” but that premise is absent. Add a concrete visible data/query constraint if the intended answer depends on selective retrieval, or replace the distractor with an alternative that actually violates a stated contract. Do not make an unstated performance preference decisive.

## Source and criteria

The existing BIZQ-01 criteria require one best-supported choice (§4.1), a meaningful learner decision (§4.2), plausible options without a systematic longest-key cue (§4.3), and causal rather than paraphrased Reason with aligned Details (§4.4); question and option identity are governed by §5C. The prompt’s Repository objective and the answer’s boundary are consistent with the cited primary references: [Microsoft’s persistence-layer guidance](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/infrastructure-persistence-layer-design#the-repository-pattern) describes domain interfaces with persistence-specific adapters and cautions against one repository per table, while [Microsoft’s domain-model guidance](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/net-core-microservice-domain-model) places repository contracts in the domain and implementations in infrastructure. Those references support the mechanism; the item-specific facts above, not source generalities, support each keyed choice.
