# Q13: actual active-session content update feasibility

Date: 2026-10-05. Bounded repository/source and compiled-bundle review only. The existing compiled bundle was inspected read-only; no device, service, process environment, account, or runtime state was inspected or changed.

## Finding

The inspected compiled app bundle is a smoke-mode build, not evidence that a device is currently running that bundle. It contains the smoke-only Premium offer module and its single AWS local fixture. That establishes an available test path for that one AWS node package when the device-local Premium test switch is enabled; it does not establish a newer package version or any OOD package offer. The current admitted OOD artifact in that bundle is statically bundled as version `object-oriented-design-interview-authoring-v2026.10.05-bizq01-24`, 1,413 questions, SHA256 `9df476e414158da0f33e118c06ed7fbc476b53bc8f0a115a470f61f9c1bf1ea3`. The runtime catalog imports that generated artifact and lock, caches the built catalog, and resolves session items by their exact track/contentVersion/artifactSha256 reference. It does not substitute a newer bundled artifact for an old session reference.

The in-app installer is a separate Premium node-package path. It requires an available offer, obtains a package from the authenticated API (or a smoke-only local fixture), verifies the response, stores the immutable package and advances its active pointer, then registers that exact node runtime. The inspected bundle selects the smoke offer module; it contains exactly one local AWS offer with one `choice_single` fixture question at `aud04_local_smoke_fixture`. The production/sandbox offer registry remains empty. Reinstalling that same fixed `aud04-local-fixture-v1` payload would not demonstrate an update to a newer package identity. No OOD full-track or OOD node offer is present. The generic installer and its memory-store tests do not provide an OOD update route.

The ordinary app bootstrap verifies the bundled catalog and then resolves an active session against its pinned artifact. If a previously recorded unavailable-active-session record exists, the gate offers the explicit abandon flow. A direct exact-artifact resolution failure during resume instead reaches the existing blocking bootstrap error; it does not migrate the active session to a new artifact or silently replace its content. The current release configuration disables Expo Updates and automatic checking; no app code calls an OTA update/fetch/reload API. Thus a genuine full-track active-session update test would require a second admitted app/content bundle version installed while retaining a session created against the first version. This preflight did not create or install another bundle, publish a candidate, or use JavaScript reload to simulate an update.

## Existing paths and constraints

- Full OOD track: generated canonical artifact and content lock are build-bundled; `syncBundledContentRelease.mjs` validates and writes the generated release files. This is not a runtime package download API.
- Session identity: session item references retain exact content version and artifact hash; resume calls `resolveExactArtifact` for that identity. There is no latest-version fallback.
- Installed node packages: `installPremiumNodeOffer` is reached from the Premium offer UI and is node-scoped. Metro binds `premiumNodeOffers.smoke.ts` when `PATTERNLY_RUNTIME_MODE=smoke`; that module exposes one `local_smoke_fixture` AWS offer and returns its fixed v1 fixture bytes. The device-local Premium testing key makes that local offer available only in the smoke runtime. Metro binds `premiumNodeOffers.disabled.ts` for sandbox/non-smoke profiles; that registry is empty and its transport returns `null`. The inspected bundle embeds `EXPO_PUBLIC_PATTERNLY_RUNTIME_MODE=smoke` and module `src/content/application/premiumNodeOffers.smoke.ts`; this is build evidence, not proof of the currently running simulator bundle. Neither profile supplies an OOD full-track or OOD node update.
- Active-content mismatch: bootstrap checks previously recorded unavailable-active-session records before resume; that specific state exposes the existing abandon flow. A direct exact-artifact resume failure is a blocking bootstrap error. Neither path migrates a session to new content.
- OTA: `app.config.js` sets release updates to `enabled: false` and `checkAutomatically: "NEVER"`; the repository contains no `Updates.checkForUpdateAsync`, `fetchUpdateAsync`, or `reloadAsync` application path.

## Feasibility decision

With only the current authorized/admitted artifact and current app runtime, Q13 cannot demonstrate a real canonical OOD package update during an active session. The verified evidence supports the current artifact and ordinary session pinning, plus the smoke-only AWS node fixture installation path. A later OOD test would need a genuinely admitted second OOD bundle/runtime and a session created under the old exact artifact, followed by a real app update/restart and exact-session resume check. The existing AWS fixture is a different node and a fixed single-version payload; it does not stand in for an OOD update. Do not edit profile storage, seed a session, alter source, or reload JavaScript to claim an update occurred.

This is a feasibility result, not a product defect, release gate, native acceptance, or full BIZQ-01 conclusion. No new implementation, config, testing service, or product policy is proposed.

There is a concrete active-session compatibility gap in source. At the v03 app commit, `TrainingSession` stored `contentVersion` but no aggregate artifact SHA, and each item ref was `{trackId, itemId, contentVersion}`. Current code requires the aggregate `artifactSha256` and refs `{trackId, questionId, contentVersion, artifactSha256}`. The current `isTrainingSession` guard is exact-keyed and rejects the old shape; its canonical record envelope and storage key prefix are still `patternly:canonical:v1`. The storage metadata schema remains version 1, and `openCanonicalRepositories` only validates metadata/provisions the guest—it has no old-session conversion. A v03 active session therefore cannot reach the current exact-artifact resolver through the ordinary current session reader; it is expected to fail closed while reading the old session, before the existing unavailable-content/abandon path can handle it. This is a source-level compatibility finding, not a device observation.

The standard current content synchronizer also does not provide a supported way to substitute the old Coding artifact into current app code: `syncBundledContentRelease.mjs` accepts a producer checkout path, builds from that checkout's current source, then enforces the current nine-track/16,077-question inventory. It does not accept an arbitrary historical artifact or release-lock entry. The v03 artifact remains available through its old app bundle in Git, but manually patching current generated artifact files would not be an admitted current-code build.

The smallest useful same-install probe, if the intended behavior is to preserve/resume active work, is: build/install the historical v03 app without uninstalling; use its normal UI to start an ordinary Free N01 session and leave it active; install the accepted current v04 app over the same app identity; launch and observe exact session resume. No seeded storage or fabricated history is needed. Current source predicts that this probe will block on the incompatible persisted session shape, rather than demonstrate successful resume. If that behavior is unacceptable, an explicit compatibility/recovery decision and implementation are needed before calling this a passing update test. A negative characterization would still need to retain the existing user data and report the precise bootstrap result. No build, install, simulator operation, session creation, or state inspection was performed for this preflight.

## OOD v23 to v24: N01 content is labeled free, but Design sessions are Premium-gated

The accepted OOD v23 app (`ea4f3d61b39bab6b9f12ace73b34721d0d6e717a`) and v24 app (`fa95d027076e970d71dacf0d1fd7976fa0ba8f60`) have byte-identical Design mode, product-mode configuration, Practice Hub/setup, lifecycle authorization, and Premium lifecycle test files. The accepted v23 and v24 content commits also carry the same OOD free-node profile (SHA256 `53ad0c90cc4e9c23a5d354ba664890c310a051934b9e1b7daaa2c56ad2b2ec31`). That profile selects N01, `requirements_use_cases_domain_vocabulary_and_model_boundaries`, with 136 ordinary pool items. Its three configured modes request 1/10, 10/20/40, and evidence-conditioned 1/10/20 items respectively.

The profile’s `freeNodeId` describes the selected content pool; it does not grant Free session access. In both app revisions, `requiresPremiumProductMode` returns true for every `isDesignInterviewModeId`. The Practice Hub calls `authorizePremiumSessionStart` before navigating to setup, and `TrainingLifecycleUseCases.startSession` authorizes before preparation. The setup route accepts only Design modes for a Design-family track. The existing Premium lifecycle test enumerates all four Design modes and checks that denied access stops before package resolution, preparation, or session mutation. Thus the ordinary OOD N01 session cannot be started through the current normal Free path without Premium authorization. The same-schema v23→v24 installation remains technically relevant only if a valid Design-session entitlement is available; the AWS-only smoke offer does not establish that entitlement.

This conclusion distinguishes content-pool selection from session admission. It is based on source and accepted content profiles at both commits, not a device or entitlement-service observation. No setting, entitlement, service, app, or session was changed.
