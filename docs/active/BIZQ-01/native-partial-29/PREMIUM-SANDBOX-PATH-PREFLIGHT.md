# Premium sandbox path preflight

**Finding: the Settings Premium switch does not provide Premium admission for ordinary OOD.** Every Design Interview product mode requires Premium. The actual start path in `PracticeHubScreen` calls `account.authorizePremiumSessionStart`; this denies a Guest, and for an authenticated account it requires either an account-bound offline Premium entitlement or a fresh server verification. The Settings override is not called by this admission path.

The repository has two distinct mechanisms that were easy to conflate:

- **Settings override and local package fixture:** Settings exposes “Premium testing” in both sandbox and smoke runtime modes and stores a device-local flag. The only runtime consumer outside Settings is `premiumNodeOfferAccess`, which checks that flag only for a `local_smoke_fixture`. Metro aliases that offer module to the smoke implementation only when `PATTERNLY_RUNTIME_MODE=smoke`; sandbox builds use the disabled module, whose offer list is empty. The smoke implementation contains exactly one AWS Certified Solutions Architect `certification-focus-practice` fixture. That control is not wired into `authorizePremiumSessionStart`, and its fixture does not contain an OOD track or Design mode. Thus it cannot admit ordinary OOD in sandbox or smoke.
- **Authenticated entitlement admission:** A previously entitled sandbox account can use the existing OOD path without a new store transaction. The code checks a fresh entitlement response online, or an account-bound cached entitlement only when reachability is confirmed offline. Sign-in/registration screens exist, but creating an account is not an entitlement grant. The repository has no trusted Premium sandbox test identity or credentials, and this preflight did not query remote accounts; whether an already entitled test account exists outside the repo remains unknown.
- **Real purchase path:** `PremiumPurchaseScreen` only creates its adapter on iOS and only when `readPurchaseConfig` returns configuration. It derives the account ID from an authenticated backend account, requires current legal acceptance and explicit instant-start consent, loads a matching monthly RevenueCat package, records purchase confirmation with the backend, invokes RevenueCat, then refreshes the backend entitlement. Guest users are explicitly told an account is required.

The backend `dev:smoke` path is a separate emulator-only fixture. `patternly-backend/scripts/dev-smoke.ts` installs `localSmokeRevenueCatEntitlementReader`; in `localSmoke.ts` the default state is `expired`, and only the explicit `PATTERNLY_LOCAL_SMOKE_ENTITLEMENT_STATE=active` setting produces a synthetic active result. The script requires Firebase Auth and Firestore emulators and explicitly excludes remote RevenueCat; its tests exercise that local route contract. It can test admission plumbing in an isolated smoke setup, but it is not provider evidence and does not grant the ordinary sandbox app a Design entitlement. The previously recorded native29 run was Guest; root reported its smoke fixture default-expired. I did not inspect a live device, API process, or environment value for this preflight.

The real-purchase method is currently disabled by legal configuration: `legalVariables.ts` selects the local fixture for every non-release mode, and both that fixture and the release legal JSON set `premiumCheckoutEnabled` to `false`. A Node 22 source-level probe using a dummy public key and dummy account ID returned `checkoutEnabled: false` and `config: null` in both `sandbox` and `release` runtime modes. This describes checkout availability only; it is not an additional BIZQ acceptance gate when an existing backend-entitled test account can be used. No secret or `.env` value was read.

The EAS `sandbox` profile is an internal build using the `preview` environment and sandbox runtime mode. `app.config.js` requires the iOS RevenueCat public key and Firebase public configuration for a sandbox iOS build; the profile file does not establish whether those remote environment values, an offering, Apple sandbox product, backend entitlement, or an entitled tester account exist. The local sandbox launcher requires `.env.sandbox.local`; the filename inventory contains the example file but no local sandbox file. Smoke uses a loopback API and Firebase Auth emulator and has local E2E credential overrides; it is not the real sandbox backend/store path. No environment values were read.

`AccountEntryScreen` contains actual sign-in and registration flows (email/password and configured Apple/Google provider flows); the repository contains no trusted Premium sandbox test identity or credentials. An account could only be prepared through the real sandbox identity/backend after that environment is independently shown to be configured. This preflight does not create an account, query remote configuration, run a build, or interact with the store.

**Decision for this slice:** neither the Settings switch nor the smoke fixture is a repository-only route to an ordinary OOD Premium session. If an existing authenticated sandbox account already has a valid backend Premium entitlement, the current Design admission path can use it without a purchase. No such profile is evidenced in the repository, so availability of that external account remains unverified. Checkout being disabled limits the optional purchase/restore method; it does not by itself block the broader BIZQ package or establish a new release gate. The evidence supports the existing-account route if a verified entitled tester is available; it does not establish that one is configured. Do not grant a local entitlement or weaken the Design admission guard to make the session start.

## Evidence

The narrow Node 22 test command

```sh
PATH=/opt/homebrew/opt/node@22/bin:$PATH ./node_modules/.bin/tsx --test \
  src/infrastructure/purchases/index.test.ts \
  src/application/trainingLifecycle/premiumProductModePolicy.test.ts \
  src/application/trainingLifecycle/premiumProductModeLifecycle.test.ts
```

passed 12/12. It confirms the adapter requires a configured account/key, is iOS-only, validates the monthly product terms, and that Design modes require Premium before session preparation. A second Node 22 command covering premium-session admission, Premium override storage, smoke fixture isolation, and Premium entry points passed 8/8. Source inspection confirms the override has no call edge into the authenticated Design admission function. The separate source-level probe returned `null` purchase configuration with the legal default in both runtime modes. In `patternly-backend`, `PATH=/opt/homebrew/opt/node@22/bin:$PATH ./node_modules/.bin/tsx --test tests/localSmoke.test.ts` passed 5/5, including default-expired and explicitly synthetic-active fixture cases; it does not verify a real provider entitlement.

This is repository feasibility evidence only. It does not establish current EAS environment values, current installed binary mode, StoreKit/App Store Connect configuration, RevenueCat offerings, backend sandbox readiness, account availability, or any transaction/entitlement result.
