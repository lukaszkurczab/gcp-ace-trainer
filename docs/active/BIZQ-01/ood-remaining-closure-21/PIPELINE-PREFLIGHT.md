# OOD remaining-closure pipeline preflight

Read-only implementation and consumer trace for a possible package after OOD closure20. This is a scope preflight, not a semantic verdict on N05–N09 and not approval to edit or admit content. The separate source review must bind its findings to the current whole questions and exact IDs before package scope is chosen.

## Inventory and scope boundary

The current bundled OOD artifact is content version `object-oriented-design-interview-authoring-v2026.10.04-bizq01-20`, with 1,413 questions. N01–N04 account for 612 questions; the remaining nodes N05–N09 have 801 questions across 45 mental units: N05 9 units/153 questions, N06 10/180, N07 8/144, N08 9/162, and N09 9/162. These are current inventory counts, not a proposed replacement count or a rule that every unit needs rewriting.

The governing spec requires an exact item-level defect/decision/identity manifest before editing (§3, especially [the batch table contract](../../../specs/business-quality/01-BIZQ-01-JAKOSC-PYTAN-I-OBJASNIEN.md:58)); each item must have a visible decisive condition, a nearest alternative that fails, and a transfer condition (§4.1, same spec:68–75). Section 8 explicitly prohibits bulk generation and a full-bank refactor ([spec §8](../../../specs/business-quality/01-BIZQ-01-JAKOSC-PYTAN-I-OBJASNIEN.md:186)). An `owner_preserves_contract` marker alone does not establish a defect. Scope therefore follows confirmed item findings, not all 801 questions or a nine-node quota.

## Existing source proof is closed and versioned

Closure20 provides the working example for a mixed proof: its private descriptor pins an exact proof SHA, before/current versions and question-set hashes, nine source paths, and separately enumerated `replacements` and `sameIdCorrections` ([`verify-migration.mjs`](../../../../../patternly-content/scripts/content/verify-migration.mjs:6430), [`proof keys`](../../../../../patternly-content/scripts/content/verify-migration.mjs:9765)). The validator checks the proof bytes, fixed descriptor, current catalog version and question-set hash, exact source membership and source bytes, whole before/current question objects, identity action, and then reconstructs and validates the predecessor ([cohort20 validator](../../../../../patternly-content/scripts/content/verify-migration.mjs:10354)). Semantic proof loading dispatches on explicit content versions; unsupported versions fail if any fixed OOD proof is present ([loader and closed proof list](../../../../../patternly-content/scripts/content/verify-migration.mjs:10552)).

This demonstrates that a future version can represent a reviewed mixture of true replacements and same-ID corrections without relaxing the fixed-proof contract. The minimal safe extension is a new fixed version step with its own exact proof hash, source/question-set bindings, complete before/current objects, and closed version dispatch; it must reconstruct version20 and preserve every prior proof unchanged. Any shared validation helper should be considered only after the actual version21 shape exists, and should accept internal frozen descriptors only. A caller-controlled mapping, arbitrary waiver, or general “migration override” is not supported by this architecture and is unnecessary for the demonstrated use case.

The current app content lock bundles the 1,413-question version20 OOD artifact. Current ordinary OOD practice remains the three configured N01 modes with 136 questions; the free-node mapping and expected pool size are pinned in [`productModeConfig.test.ts`](../../../../../patternly/src/content/canonical/productModeConfig.test.ts:30) and lines 165–180. ## Coherent package versus nodewise updates

No source-quality findings were produced by this preflight, so choosing “one package for all N05–N09” would be premature. A package21 spanning several nodes is a reasonable hypothesis only if the independent semantic audit confirms a connected set of item-level defects whose shared correction and cross-node duplicate review are clearer together. It could then receive staged whole-object semantic review by node/mental-unit groups, followed by one frozen exact mixed proof and one source→app artifact→candidate/admission integration. The 801 inventory is not its scope.

If confirmed defects are isolated to one node or an unrelated small set, nodewise packages are simpler to review and limit proof coupling; the cost is another content version and the corresponding app lock/candidate/web provenance cycle for each accepted package. Conversely, bundling unrelated edits only to avoid those cycles creates a larger proof and increases review/reconstruction coupling without a confirmed quality benefit. Choose after item-level semantic findings and exact ID/identity actions are known. Do not skip staged independent review to achieve a single integration.

## Verification dependencies and boundaries

For whichever exact scope is approved, the producer side needs the existing question contract/scorer checks plus fixed proof verification, exact source/question-set hashes, predecessor reconstruction, and negative tests for missing, extra, duplicate, altered or symlinked proof/source inputs. Historical tests must prove exact version20 and earlier snapshots remain recoverable. App verification should assert source-to-bundle parity for the approved items, unchanged outside items and N01 pool membership, correct score under option-order reversal, feedback target alignment, and the existing release-lock/candidate/admission bindings. Web provenance checks follow the current exporter/consumer contract. These checks establish the changed package and its consumers; they do not establish full BIZQ-01 closure, native-device coverage, Premium/provider eligibility, or a semantic verdict on every OOD item.

No producer/app/web tests were run for this read-only preflight. No source, proof, artifact, lock, admission, or historical fixture was changed.
