This confirms the serialization and ordering assumptions against the real files; it does **not** freeze the N05 identity map, prove the proposals semantically accepted, or authorize source/proof integration.

## What the current verifier actually does

The closed20 implementation is the private `validateBizq01OodCohort20Proof` function in [`verify-migration.mjs`](../../../../../patternly-content/scripts/content/verify-migration.mjs#L10355). `verifyMigration` is the public entry point; there is no exported generic reconstruction helper.

The fixed proof binds an exact proof-file hash and descriptor, nine fixed source paths with their before/current byte hashes and taxonomy, all replacement and same-ID entries, complete `beforeQuestion` and `currentQuestion` objects, the accepted option ID, and fixed question-set hashes. Validation checks source paths and proof bytes, source membership/order and taxonomy, equality with canonical current questions, and each fixed entry against the proof descriptor. For each source it maps each current question ID to its exact `beforeQuestion`, leaves unchanged items as-is, sorts the predecessor by `questionId`, serializes with `JSON.stringify` **without a trailing newline**, and hashes those bytes against `beforeSourceSha256` (implementation lines 10510–10515). It then validates the immutable predecessor chain by loading the fixed 19a proof from the reconstructed predecessor catalog (version19a) (around lines 10539–10555). The existing closed20 proof and predecessor evidence should stay byte-immutable.

The existing path also has cohort-specific option-ID restrictions (lines 10437–10508): it rejects repeated option IDs across all current cohort questions and finally rejects any current option ID found anywhere in the predecessor cohort. The current question contract only requires option IDs to be unique inside one question’s own option list ([`question-contract.mjs`](../../../../../patternly-content/scripts/content/question-contract.mjs#L174)); `scoreQuestion` receives the question object and compares the response option ID with that question’s answer ([same file](../../../../../patternly-content/scripts/content/question-contract.mjs#L542)). The builder separately enforces question IDs across a track. The wider closed20 sets are therefore package-specific, not a global option-ID contract. Every old N05 source item uses the same `owner_preserves_contract` option ID; the current B02–B04 drafts still use it on 51 items across distinct question IDs. A verbatim copy of the cohort-wide checks would reject those same-ID draft objects. Do not copy those guards into N05 without a contract-backed reason. The fixed N05 proof must bind each exact old/current question, per-item identity action, and accepted option ID. Apply retired-question checks only to actual retired identities; for same-ID entries, option-ID continuity is a per-item meaning decision, not global cross-question uniqueness. Independent identity review must settle the map and each option meaning before bindings are frozen. This is a scope distinction, not a request for a general option-ID exception.

The N05 verifier is not callable with an arbitrary descriptor, so I did not claim that it directly accepted an N05 package. Separately, I applied its exact in-memory reconstruction operation to the real N05 inputs: read each raw source array, use the current draft question IDs to look up the corresponding original source object (the current proposals retain the same IDs at this stage), sort by `questionId`, and serialize with `JSON.stringify` without a newline. All **9/9** reconstructed byte buffers exactly equaled the original files. The existing nine raw files also each equal `Buffer.from(JSON.stringify(JSON.parse(raw)))`; a newline changes every raw hash. This is a serialization probe of the draft ID hypothesis, not proof data, an accepted map, or a producer helper invocation.
