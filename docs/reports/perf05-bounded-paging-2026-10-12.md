# PERF-05 — bounded backend paging, 12.10.2026

## Cel i ustalenia przed implementacją

Wymaganie produktu: istniejąca synchronizacja paginowana, bez utraty/powielania faktów, zgodnie z root docs/02 i08 oraz istniejącym PERF-05 w specyfikacji performance. Backend4d8efbd6 czyta całą kolekcję przy każdej stronie, route sortuje logical identity i szuka kursora. Appae35f8a1 już pobiera pageSize100 i traktuje token jako opaque; restore następuje dopiero po kompletnym getProgress. Full readSnapshot pozostaje wymagany przez adoption/transfer i nie jest compatibility fallbackiem paginacji. App production zawsze żąda explicitpageSize100; backendowe no-query testy nie dowodzą zależności produkcyjnego konsumenta od unbounded endpointu. Pełna bramka później potwierdziła, że jeden test adopcji czytał201records; dostosowano go do pełnego bounded sweep (szczegóły poniżej).

Hipoteza: readPage w canonical FirestoreProgressStore, documentId order, limit pageSize+1. Kursor nowego zamkniętego tokenu v2 wskazuje pierwszy niewysłany dokument (lookahead), następna strona startAt(cursor); wymagana zgodność pierwszego ID wykrywa nieistniejący cursor bez dodatkowego progress point-read. Brak backfill/projection/indexów złożonych. Wszystkie GET, także bez parametrów, mają default100; usunąć pełny snapshot/sort/slice z trasy. Stare tokeny v1 są jawnie invalid, bez dual implementation; klient jest opaque. Token związany z user/revision/generation, checksum jest integralnością formatu, nie uwierzytelnieniem.

Konto oraz syncMetadata odczytać przed query i świeżo po query; sprawdzić aktualne active authorization generation requestu, revision/generation i metadata updateTime, także promotion lease. Odrzucić race zamiast retry/fallback. Zachować strict toView record validation. Race po finalnym readback jest poza liniaryzacją odpowiedzi; kolejna strona odrzuci zmienioną rewizję. Każdy zaakceptowany writer musi atomowo zwiększać revision lub generation z danymi; sprawdzić to w aktualnych producerach, nie zakładać dla zewnętrznych bezpośrednich zapisów.

Weryfikacja: najpierw mały bezpieczny probe rzeczywistego Firestore SDK/emulatora w istniejącym isolated runnerze/demo namespace. Następnie baseline i after dla N100/1k/10k, pageSize100, query/returned document counts i median/p95 pełnego sweep; identyczne logical datasets/outputhash. Nie nazywać tych liczników billing units. Testy stale/invalid/cross-account/nonexistent cursor, generation/revision/auth changes, zapis między metadata/query oraz query/readback, corrupt records; pełny producer→mobile consumer→restore proof. Narrow checks i wymagane bramki repo; nie zmieniać timeoutów ani danych użytkowników. Testy runtime API nie zastępują native acceptance.

Bramki wydania: cloud deployment/index approval i final iOS acceptance osobno, nie warunki samego source odbioru. Zgoda na poprzednią publikację backendu nie jest automatycznym poleceniem kolejnego deployu zmienionego kontraktu. EAS Android jest osobnym zamówionym buildem istniejącego accepted source.

Kolejność implementacji: backend contracts/store/query+tests → app consumer tylko jeśli wykazana potrzeba → joint proof/OpenAPI/required gates. Kolejność source merge: backend producer, następnie ewentualny app consumer z exact pin. Kolejność deployment: po osobnej właściwej autoryzacji, gotowy backend przed klientem wymagającym nowego kontraktu; obecny klient ma zachować opaque token behavior. Root writer, Luna High independent design i końcowy QA, bez potomków.

Ocena hipotezy root: dopasowanie0,94; prostota0,90; ryzyko0,84; utrzymywalność0,92; minimum0,84. Decyduje zachowanie jawnych fences i jeden bounded path bez migracji. Review ma samodzielnie rozstrzygnąć spójność snapshotu i koszty, wskazując blocker z wymaganiem lub konkretnym ryzykiem. Do czasu review i pomiaru brak material implementation.
