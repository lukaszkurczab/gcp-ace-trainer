## Cel / ustalenia / podejście

Pięć istniejących typów choice_single, choice_multiple, ordering, complexity, decision_matrix otrzymuje pionowych właścicieli validation, completeness, scoring/diagnostics, feedback contract oraz renderer binding. Obecne questionTypes/Validation/Scoring i canonicalInteractionPresentation zamykają te reguły w globalnych uniach/dispatchu. Lifecycle przyjmuje już unknown response, lecz contracts/package owner nadal eksportują concrete Question/CanonicalTrackRuntime. Nie zmieniamy serialized payloadów/odpowiedzi, schema, kluczy ani pinów.

Każdy vertical module ma konkretne lokalne typy. Wspólna granica zawiera neutralne metadata/exact ResolvedContentRef i nieprzezroczysty validated interaction; registry w composition wiąże unikalny authored interaction.type string z handlerem. Family dostaje required InteractionPort; nie zna zamkniętej unii payloadów. Package/lifecycle nie wystawia CanonicalTrackRuntime/Question jako alternatywnej rodzicielskiej ścieżki: używa neutralnego catalog/package portu. Registry/validator jest wstrzyknięte przy istniejącym exact catalog/package boundary; pełny artifact jest walidowany przed udostępnieniem, nie tylko wybrany item. runtimeCatalog/domain nie importuje app composition lub UI wstecz. Parser handlera waliduje unknown question/response, a rezultat zawiera completeness, AttemptResult, diagnostics i authored feedback. Brak/unknown/duplicate handlera daje preparation failure przed session write; malformed authored payload zawodzi przy exact package ingress. Nieprawidłowa/niekompletna/obca odpowiedź zawodzi przed J; prawidłowa błędna odpowiedź zachowuje obecny score i partial semantics.

Renderer binding należy do UI warstwy tego samego vertical module; core nie importuje React ani features. Lokalne typowane view models mogą korzystać z obecnych prezentacyjnych Choice/Ordering/Dimension primitives. Shared registry wybiera binding po interaction identity, bez wymaganej closed renderer union lub shared switch. Nie tworzyć service locator ani nowego generic frameworka.

Family zachowuje selection/review/evidence/recommendation i disclosure semantics. Handler produkuje feedback data; nie autoryzuje ich ujawnienia. Lifecycle nadal jeden coordinator i journal writer. Coding może pokazać feedback po zatwierdzonym trwałym pending J; Certification practice i Design wymagają odpowiedniego materialized attempt. Nie scalać tych granic. Failed journal nie ujawnia feedbacku. Nie przeliczać authored explanations ani zmieniać ordering adjacency/omission logic/source links.

## Pełne kryteria

1. Każdy z pięciu obecnych typów ma jednego ownera validation/completeness/score/diagnostics/feedback/rendererbinding; brak required shared closed union i wspólnego dispatch wymagającego edycji przy rozszerzeniu.
2. Schema→completeness→score→feedback→renderer i rzeczywisty runtime response round-trip zachowują obecne pięć zachowań, dokładny content pin, authored messages/source/course i wynik BIZQ.
3. Testowa szósta interakcja działa wyłącznie przez nowy module/registration, bez edycji kernel/persistence/shared switch. Nie jest produktem/admission nowego contentu.
4. Unknown/unregistered/duplicate handler, malformed authored payload, foreign/malformed/incomplete response, sparse/duplicate/extra keys i zmiana exact identity jawnie odrzucone. No default guessed answer/score/explanation.
5. UI handler bindings nie importują scorer ani review mutation; family/runtime nie importują UI, innej family lub repository implementation. Jeden istniejący lifecycle/J/store.
6. Feedback pozostaje za właściwą durable boundary dla każdej family/mode; failedJ/no materialization cases nie ujawniają niedozwolonego feedbacku. Handler registry nie poszerza family/mode admission.
7. Końcowa integracja ARCH-02 pokrywa rzeczywistą kompozycję trzech rodzin i journal recovery/exact resume; meaningful narrows/TC/fullgate, niezależny QA i exact CI przed odbiorem.
