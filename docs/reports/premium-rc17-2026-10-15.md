## Cel i decyzje

Wdrożono [odebrany kontrakt16](../specs/engineering/premium-revenuecat.md#kontrakt-16--tożsamość-i-odroczona-transakcja-15102026), bez powtarzania06/10/16. Backend pozostaje autorytetem Premium. Nowy wspólny resolver używa `purchaseAttempts/{confirmationId}`, nie „ostatniej” zgody. `purchaseLocks` jedynie serializuje próby. Atomowy claim dopuszcza dispatch tylko raz; retry nigdy nie odnawia zgody ani SDK efektu. Exact SDK transaction ID jest kandydatem, a zaufany webhook niezależnym potwierdzeniem.

Globalny klucz to SHA256 jednoznacznie kodowanej tablicy `[RevenueCat projectId, appId, APP_STORE, environment, transactionId]`, bez ownera i SKU. Konsumpcja zgody, globalne związanie i jeden logiczny receipt są atomowe. Obie kolejności webhook/kandydat oraz retry po ACK wracają do tego samego resolvera. Zachowano receipt ID SHA256(transactionId), aby nie powielać wcześniejszej przestrzeni M10; istniejący inny receipt daje jawny konflikt.

Okno wymaga acceptedAt ≤ initiatedAt ≤ purchasedAt < startExpiresAt; dokładnie15min jest poza nim. Czas dostarczenia eventu nie służy korelacji. Unknown/pending nie zwalnia blokady. Cancel/reject z oryginalnego SDK wywołania zamyka próbę; jego nieznany transaction ID nadal jest historią mogącą wykluczać automatyczne przypisanie późnej płatności do kolejnej próby. Znany inny transaction ID starszej zamkniętej próby nie blokuje nowego dokładnego zakupu. Legacy `active` nie jest źródłem korelacji: istniejąca niezużyta próba jest leniwie projektowana do historycznej sprawy, bez domyślnego initiatedAt/scope umożliwiającego bind, i wymaga jawnego zamknięcia.

Zatwierdzony owner/custom UUID, original ID, app, SKU, środowisko i sklep są kontrolowane. Reader wymaga `app_store`; pole app_id nie jest wymyślane dla odpowiedzi subscriber API v1. Zakres klucza odczytu/aplikacji wymaga osobnego odbioru usług. TRANSFER i alias/wrong-owner zapisują incydent oraz sticky odmowę na aktywnych kontach; zero przenoszenia projekcji, zgody i receipt. Odmowa obejmuje fresh entitlement i końcowy admission pakietu, również po await odczytu treści. Incydenty są widoczne właścicielowi/operatorowi. Nie dodano authority kasującej marker; późniejsze operacyjne wyjaśnienie RC wymaga osobnego zatwierdzonego kontraktu. Usunięte konto nie jest odtwarzane, event metadata nie utrwala raw affected UUIDs.

## Osiągalność i cykl danych

- Uwierzytelnione API udostępnia exact status, claim/candidate/pending/cancel oraz bounded sprawy właściciela. Operator ma ścisłe uprawnienia `purchase_cases:read/resolve`, show/action w istniejącym CLI, revision i stabilne operation ID. `bind` wymaga wskazania niezależnie zweryfikowanego dokładnego wyniku oryginalnej operacji/provider, zgodnego transactionId i initiatedAt. Same daty/SKU nie wystarczą. Brak dowodu daje close_unresolved; release lock jest jawne. To implementacja komendy i walidacji, nie wykonana operacja na usługach.
- Po30dniach backend odmawia nowej konsumpcji i pokazuje expired_unresolved niezależnie od purge. Po90dniach istniejący retention service kompaktuje payloady do minimalnego stanu/deduplikacji, zachowując immutable confirmations/receipts. Billing postcheck nie zgłasza complete przy due rekordzie dopisanym po skanowaniu.
- Eksport zawiera allowlisted purchaseHistory bez innych właścicieli, actorów i SMTP claim payloadu. Mobilny eksport zachowuje nowe dane; starsze zapisane pliki v1 pozostają czytelne. Usuwanie konta usuwa globalny indeks oraz dzieci resolutions pod istniejącym fenced cleanup.
- Jeden dispatcher obsługuje webhook, kandydata i operatora. Ready/failed claim atomowo zapisuje durable delivery attempt przed SMTP. Pending/expired lease/unknown nigdy nie powodują resend; finalizacja wymaga exact claim/lease. Brak verified kontaktu jest jawny. Zasady [M10](../../../patternly-backend/docs/purchase-receipt-delivery.md) zachowane.
