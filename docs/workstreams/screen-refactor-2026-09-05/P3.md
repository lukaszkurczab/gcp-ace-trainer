The repository plan records the independent Luna/max briefing validation from P0: consistency `0.88`, simplicity `0.84`, risk/safety `0.82`, maintainability `0.87`, minimum `0.82` approval. The approach keeps scheduler and persistence contracts unchanged, adds one local request guard for behavior that must be tested, and leaves native-facing work inside the existing platform boundary.

## Confirmed facts and assumptions

- `useNotificationSettings` previously had no visible loading/error state, lifecycle refresh, synchronous mutation guard, or stale-read protection. Screen handlers allowed rejected Promises to escape.
- `NotificationSettingsScreen` used the same checking copy for `null` and `undetermined`; the existing reminder row was fully disabled for denied permission even when a saved reminder could still be turned off.
- `SettingsBottomSheet` exposed its Close action only on the backdrop, outside `accessibilityViewIsModal`; its content was already scrollable and owns the notification editor actions.
- `notificationPreferences.ts` and `notificationSettingsRepository.ts` remain the scheduler/rollback and persistence owners. They were intentionally not changed.
- Foreground refresh is represented by `AppState` moving to `active`. A refresh that starts while a mutation is busy is skipped because its result cannot be safely applied; the mutation result remains authoritative.
- The native screen was not rerun in this stage because the request explicitly excludes Metro/native/full baseline runs. Focused source and model tests establish the async and presentation contracts; native keyboard and permission dialogs remain P5 evidence.

## Changes

- Added `notificationSettingsState.ts`, a narrow request guard that rejects concurrent mutations synchronously and invalidates reads started before or during a mutation.
- Expanded `useNotificationSettings` with `loading`, `busy`, `busyOperation`, `error`, `refresh`, and `clearError`; added mount cleanup, foreground refresh, guarded state commits, and caught operation failures.
- Updated `NotificationSettingsScreen` to render loading and retryable operation errors, catch permission/save/disable/open-settings failures, retain invalid drafts, clear draft errors on open, and disable unsafe controls while loading or busy.
- Kept the save action disabled when permission is denied while retaining the disable action for an existing saved reminder.
- Distinguished `null` permission (`Permission status is loading`) from `undetermined` (`Notifications are not enabled yet`) and denied, with EN/PL copy for all new states.
- Made the reminder input use `minHeight`, an explicit text scale cap, and vertical centering; the shared sheet now applies automatic keyboard insets and has an accessible visible Close button inside the modal boundary.
- Removed the unused `locale` and `AppLocale` imports from the notification screen.

## Risks and limits

The hook still calls the concrete `expoNotificationPlatform`, so native permission and Settings failures are covered by the visible screen handling and pure guard tests rather than an injected platform test harness. The skipped foreground refresh during a mutation relies on the mutation's own successful permission/settings result; a future native operation that changes state without returning it would need an explicit post-operation refresh. No native screenshot was taken after these changes, so keyboard geometry, 200% title wrapping, and device Settings return behavior still require the controller's P5 smoke pass.
