## CH-06 — usunięcie starych formatów i zapisu ukrytego w odczycie reminders

**Bieżący status:** CH-06 został odebrany dla zakresu source/local/full gate/exact CI. Bieżące [getters](../../../src/storage/repositories/notificationSettingsRepository.ts#L227) odczytują kanoniczne envelopes bez zapisu; historyczne formaty są jawnie odrzucane. Dowody i granica bez native UI/device: [odbiór CH-06](../../reports/ch06-acceptance-2026-10-12.md). To nie otwiera ponownie wymaganej pracy.

**Historyczna diagnoza:** W baseline poprzedzającym CH-06 odczyty `getDeviceReminderSettingsSnapshot`/`getDeviceReminderJournal` normalizowały i zapisywały legacy formaty, a testy oczekiwały migracji. Cancellation IDs były i pozostają używane przez bieżący runtime.

- **Obszar / problem:** accepted LearningPlan → device-local reminders; obsolete formats rozszerzają możliwe stany i wymagają utrzymywania niepotrzebnych migratorów.
- **Zakres:** `patternly/src/storage/repositories/notificationSettingsRepository.ts`, jego testy, związane testy `src/application/learningPlanReminderRuntime.test.ts`; konsumenci `notificationPreferences.ts` i inventory guards tylko w granicach usuwanego formatu.
- **Stan końcowy / AC:** odczyt DeviceReminderSettings/journal jest read-only; obsługuje wyłącznie bieżący kanoniczny format. Stare daily/practice settings i journale są jawnie unsupported, bez konwersji ani cichego resetu; żaden caller nie zamienia ich w puste ustawienia i nie nadpisuje nowym defaultem. Poprawne reminders nadal wynikają z accepted plan i zachowują revision, pending recovery i cancellation.
- **Historyczny required fix, wykonany w CH-06:** usunięto dawne typy `Legacy*`, practice reminder pre-ODK034 codecs/migrators i martwe `getStoredNotificationSettings`, `saveNotificationSettings`, `getPracticeReminderJournal`, `savePracticeReminderJournal`, `clearPracticeReminderJournal`, `isCanonicalPracticeReminder`, `isCanonicalPracticeReminderTarget`; testy sukcesu migracji zastąpiono testami jawnego odrzucenia.
- **Zachować:** bieżący DeviceReminderSettings/DeviceReminderJournal, CAS, dokładne plan/slot identity, pending native cancellations. Pole `legacyNotificationIds` obecnie służy również jako backlog bieżących niepewnych anulowań w `notificationPreferences.ts`; nie usuwać go na podstawie nazwy ani nie robić kosmetycznego rename/schema migration.
- **Testy:** storage spy potwierdzający zero zapisów podczas każdego odczytu; rejected old shapes; valid canonical roundtrip; current pending/cancel failures i retry, plan save/disable/reconcile. Existing reminder suites oraz typecheck/boundary checks.
- **Ryzyko:** umiarkowane — pomylenie compatibility z bieżącym recovery zgubi native cancellation IDs. **Zależności:** brak. **Poza zakresem:** polityka planu, scheduling redesign, migracja starych buildów, zmiana powiadomień na serwerowe.

## CH-07 — jeden sposób adresowania danych profilu, bez legacy namespace

**Bieżący status:** CH-07 odebrany source/local/exact CI oraz natywny Guest/login/logout smoke i preservation (AC9): zachowane12pierwotnychprofili/ten samGuest, jeden dodatkowy profil autoryzowanego nowego smoke account. Dowody i ograniczenia: [plan](/Users/lukaszkurczab/Desktop/Projects/Patternly/docs/PATTERNLY-WORKING-PLAN.md), [raport CH-07](../../reports/ch07-acceptance-2026-10-12.md). Nie oznacza to gotowości wydania ani odbioru PERSIST-13.

- **Obszar / problem:** profile isolation; aktywna obsługa dawnych nieskopowanych rekordów powiela reguły identyfikacji i adresowania bez wymaganego konsumenta produkcyjnego.
- **Zakres:** `patternly/src/infrastructure/storage/profileStorageRouter.ts`, powiązane legacy-kind branches w `mmkvClient.ts` i `src/application/account/AccountSessionProvider.tsx`, testy `profileStorageRouter.test.ts` i powiązane profile startup/account composition tests. Objąć także `src/storage/repositories/profileStorageRepository.ts` i testy `mmkvClient.test.ts`. Repo exports i runtime callers sprawdzić przed usunięciem symboli.
- **Stan końcowy / AC:** nowe i poprawne bieżące profile account/guest używają wyłącznie scoping po profile ID; żadna ścieżka nie kieruje do nieskopowanych historycznych kluczy ani nie odtwarza `legacy_owner/legacy_guest`. Unsupported legacy state daje jawny unavailable/reset boundary; audit/task nie autoryzuje automatycznego usunięcia cudzych danych.
- **Historyczny required fix, wykonany w zakresie source CH-07:** usunięto legacy profile kinds, bootstrap `hasCanonical → storedGuestInstallation → legacy profile`, boolean legacy w `physicalKey`, surową enumerację kluczy, testy wymagające migracji oraz nieużywane `continueAsGuestInNewProfile` wraz z re-exportem/importem. - **Zachować:** jeden bieżący Guest, izolację Guest/A/B, registry generation/checksum i dual-slot integrity, scope leases, adoption transfer/discard, explicit logout i journal recovery dla bieżących formatów.
- **Testy:** świeży Guest, guest/account A/B/A i restart, profile transition interruption, storage lease invalidation, corrupt registry fail-closed, unsupported legacy bez odczytu/zapisu user data. Testy izolacji obecnie zbudowane na `legacyOwnerStorage` przenieść na bieżące fixtures, zamiast po prostu usuwać ich coverage. Jeden istniejący iPhone17 do zwykłego guest/login/logout smoke po implementacji; bez VoiceOver.
- **Ryzyko:** podwyższone — wspólny router obejmuje każdą lokalną operację; dlatego osobny bounded slice i niezależny acceptance review. **Zależności:** brak; uzgodnić ownership z równoległymi profile changes. **Poza zakresem:** nowy engine storage, migracja instalacji preproduction, zmiana retention/reset/remote sync.

## CH-08 — testowalna finalizacja konta zamiast kombinacji flag w providerze

**Bieżący status:** CH-08 został odebrany dla bounded source/local/full gate/exact CI. [Provider](../../../src/application/account/AccountSessionProvider.tsx#L1000) przekazuje `AccountFinalizationOptions` do [wyodrębnionego executora](../../../src/application/account/accountFinalization.ts); szczegóły napraw i granice dowodu są w [raporcie odbioru CH-08](../../reports/ch08-acceptance-2026-10-12.md). Raport zachowuje nieblokującą lukę testową i nie twierdzi pełnego native acceptance CH-07.

**Historyczna diagnoza:** W baseline przed CH-08 `AccountSessionProvider` wykonywał `finalizeCurrent` z pozycyjnymi flagami. Wydzielenie ownera oraz testy stale-generation były wtedy brakujące.

- **Obszar / problem:** application account finalization; duży provider i tekstowe testy nie dają lokalnego dowodu poprawnej kolejności skutków tego jednego flow.
- **Zakres:** `patternly/src/application/account/AccountSessionProvider.tsx`: wyłącznie `finalizeCurrent` i jego call sites; istniejące `accountSessionExchange.ts`/`profileStartupCoordination.ts` jako zachowani owners; jeden testowalny moduł finalizacji w tym samym katalogu (proponowany `accountFinalization.ts`) oraz jego testy. `accountIdentityComposition.test.ts` tylko w zakresie zastępowanych flow assertions.
- **Stan końcowy / AC:** provider deleguje finalizację; nazwany context/options lub rozłączny typ wariantów zastępuje nieczytelne kombinacje positional booleans. Jeden owner kolejności wymiana sesji → profil → account data → publikacja, korzystający z istniejących guards. Każdy obecnie osiągalny wariant ma jawny test zachowania; stary UID/generation nie powoduje kolejnych zapisów/publikacji po await.
- **Historyczny required fix, wykonany w CH-08:** usunięto inline duplikat przeniesionego flow, positional boolean API i zastąpione wykonywalnymi testami assertions. **Zachować:** publiczny account context, guest adoption allow/discard, prepared-profile gates, deletion-marker semantics, existing non-blocking reminder failure policy oraz wszystkie recovery/sign-out guards. Boundary/wiring regex mogą pozostać; same regex nie zastępują testów zachowania.
- **Testy:** kontrolowane deferred ports dla stale `/me`, zmiany generacji przed profile selection/sync/publication, distinct preserved/prepared scope i adoption paths, reminder failure, sukces; istniejące coordinator/exchange/profile/account tests. Dowód złośliwego harmonogramu promises, bez prawdziwych kont i bez nowego auth frameworka.
- **Ryzyko:** umiarkowane–wysokie ze względu na kolejność skutków; nie przenosić całego providera w jednym refaktorze. **Zależności:** CH-02, CH-07 i rebase względem bieżącego AUD-08-B2 w tym pliku; brak zależności od decyzji SMTP jeśli nie dotyka flow. **Poza zakresem:** reszta account commands/UI, nowa architektura auth, zmiana produktu lub persistence protocol.
